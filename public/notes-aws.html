PART 1

IAM · 보안

누가 무엇을 할 수 있는지 정하는 IAM은 AWS 사고의 가장 흔한 원인입니다. 정책이 겹칠 때 무엇이 이기는지, 키를 어떻게 다뤄야 하는지를 상황으로 익힙니다.

정책 평가

Allow와 Deny가 겹치면

사용자 정책은 s3:*를 Allow, 그룹 정책은 s3:DeleteObject를 Deny한다. 이 사용자가 객체를 지우면?

  • 거부된다
  • 허용된다 (Allow가 하나라도 있으면)
  • 나중에 붙인 정책을 따른다
  • 사용자 정책이 그룹 정책보다 우선해 허용된다

IAM은 요청에 걸리는 모든 정책을 모아 보고, 명시적 Deny가 하나라도 있으면 무조건 거부한다. 그다음 Allow가 있으면 허용, 아무것도 없으면 거부(암묵적 거부)다. 정책을 붙인 순서나 위치(사용자·그룹·역할)는 우선순위가 없다.

정책 평가

정책이 없는 사용자

정책을 하나도 붙이지 않은 새 IAM 사용자가 s3:ListBucket을 호출하면?

  • 거부된다
  • 같은 계정이라 허용된다
  • 읽기 작업이라 허용된다
  • 루트 사용자가 승인하면 그때 허용된다

AWS는 기본이 거부다(암묵적 거부). 같은 계정이어도, 읽기여도 명시적으로 Allow한 정책이 있어야 한다. 그래서 새 사용자·역할에는 필요한 권한만 골라 붙인다(최소 권한).

정책 평가

권한 판단 순서

IAM이 요청 하나를 허용할지 판단하는 순서대로 놓으세요.

  1. 명시적 Deny가 있으면 거부
  2. 명시적 Allow가 있으면 허용
  3. 둘 다 없으면 거부

Deny 확인이 먼저라서 Allow가 아무리 많아도 Deny 하나를 못 이긴다. 마지막 단계 때문에 "아무 말 없으면 안 된다"가 기본이다.

자격 증명

EC2 앱의 AWS 권한

EC2에서 도는 앱이 S3 파일을 읽어야 한다. 가장 안전한 방법은?

  • EC2에 IAM 역할(인스턴스 프로파일)을 붙인다
  • 액세스 키를 .env 파일에 넣는다
  • 액세스 키를 AMI 이미지에 넣어 둔다
  • 버킷을 공개로 열어 키 없이 읽는다

역할을 붙이면 SDK가 인스턴스 메타데이터에서 자동으로 임시 자격 증명을 받아 쓰고, 만료되기 전에 알아서 새로 받는다. 오래 사는 액세스 키를 서버에 두면 유출됐을 때 피해가 크다. Lambda, ECS도 같은 방식(실행 역할)이다.

자격 증명

역할을 맡으면 받는 것

sts:AssumeRole로 역할을 맡으면 받는 자격 증명은?

  • 만료 시간이 있는 임시 자격 증명
  • 만료되지 않는 새 액세스 키
  • 역할 이름과 로그인 비밀번호
  • 역할을 만든 사람의 액세스 키

AssumeRole은 액세스 키 ID, 비밀 키, 세션 토큰 세 개와 만료 시각을 준다. 기본 1시간이고 정해진 범위에서 늘릴 수 있다. 세 개를 모두 써야 요청이 서명되고, 만료되면 다시 받아야 한다.

계정

팀원 계정 나누기

개발자 3명이 같은 AWS 계정에서 일한다. 로그인을 어떻게 나눌까?

  • 각자 사용자를 만들고 필요한 권한만 준다
  • 루트 사용자 하나를 셋이 함께 쓴다
  • IAM 사용자 하나를 만들어 셋이 함께 쓴다
  • 각자 사용자를 만들고 모두 AdministratorAccess를 준다

사람마다 따로 로그인해야 CloudTrail에 누가 무엇을 했는지 남고, 퇴사자만 골라 막을 수 있다. 권한은 하는 일에 필요한 만큼만(최소 권한), 조직이라면 IAM Identity Center로 사람을 관리한다. 루트 사용자는 결제 정보 변경, 계정 닫기처럼 무엇이든 할 수 있고 정책으로 제한할 수도 없다. 그래서 MFA를 켜고 액세스 키는 만들지 않으며, 일상 작업은 권한을 좁힌 IAM 사용자·역할(또는 IAM Identity Center)로 한다.

사고 대응

공개 저장소에 올라간 키

실수로 액세스 키를 GitHub 공개 저장소에 푸시했다. 가장 먼저 할 일은?

  • 그 키를 비활성화·삭제하고 새 키로 바꾼다
  • 커밋을 지우고 force push한다
  • 저장소를 비공개로 바꾼다
  • 키 파일 이름을 바꿔 다시 커밋한다

공개 저장소의 키는 자동화된 봇이 몇 분 안에 긁어 간다. 커밋을 지우거나 저장소를 닫아도 이미 복사된 키는 살아 있다. 먼저 키를 무효화하고, CloudTrail에서 그 키로 한 일을 확인한 뒤, 가능하면 키 대신 역할을 쓰도록 바꾼다.

정책 작성

Resource에 버킷 이름만 적으면

{
  "Effect": "Allow",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::my-bucket"
}

이 정책을 가진 사용자가 my-bucket의 파일을 GetObject하면?

  • 거부된다. my-bucket/*가 따로 필요하다
  • 허용된다. 버킷 ARN에 안의 객체도 포함된다
  • 허용된다. 같은 계정의 버킷이라서
  • 정책 저장이 거부된다. /*가 꼭 있어야 한다

arn:aws:s3:::my-bucket은 버킷 자체(ListBucket 같은 버킷 작업), arn:aws:s3:::my-bucket/*는 버킷 안 객체(GetObject, PutObject)를 가리킨다. 둘 다 필요하면 Resource에 두 개를 모두 적는다. 가장 흔한 AccessDenied 원인 중 하나.

역할

다른 계정의 역할 맡기

계정 A의 사용자가 계정 B의 역할을 맡으려면 필요한 것은?

  • B의 신뢰 정책에 A를, A 사용자에 AssumeRole 권한
  • B 역할의 권한 정책에 A 계정을 적기만 한다
  • A 사용자에게 AssumeRole 권한만 주면 된다
  • B 계정의 액세스 키를 A 사용자에게 준다

역할에는 두 가지 정책이 있다. 신뢰 정책은 "누가 이 역할을 맡을 수 있나", 권한 정책은 "맡으면 무엇을 할 수 있나". 다른 계정이면 양쪽이 모두 허락해야 한다: B는 신뢰 정책으로 A를 믿고, A는 자기 사용자에게 AssumeRole을 허용한다.

EC2 보안

메타데이터 자격 증명 지키기

EC2 앱의 SSRF 취약점으로 메타데이터(169.254.169.254)의 역할 자격 증명을 빼앗기는 위험을 줄이는 설정은?

  • IMDSv2를 필수로 한다 (세션 토큰 요구)
  • 보안 그룹에서 169.254.169.254를 막는다
  • 역할 대신 액세스 키를 쓴다
  • 인스턴스의 퍼블릭 IP를 없앤다

IMDSv2는 먼저 PUT 요청으로 세션 토큰을 받아야 메타데이터를 읽을 수 있어서, 단순히 URL을 대신 요청하게 만드는 SSRF로는 뚫기 어렵다. 메타데이터 주소는 인스턴스 안에서만 닿는 주소라 보안 그룹으로 막는 대상이 아니다.

PART 2

VPC · 네트워크

서브넷, 라우팅, 보안 그룹과 NACL을 헷갈리면 "왜 접속이 안 되지?"로 하루가 갑니다. 패킷이 실제로 어디를 지나가는지로 익힙니다.

서브넷

퍼블릭 서브넷의 조건

서브넷을 퍼블릭 서브넷으로 만드는 것은?

  • 라우팅 테이블에 인터넷 게이트웨이로 가는 경로
  • 서브넷 이름에 public을 붙이는 것
  • 보안 그룹에서 0.0.0.0/0을 허용하는 것
  • 서브넷에 NAT 게이트웨이를 두는 것

서브넷의 성격은 라우팅 테이블이 정한다. 0.0.0.0/0 → igw-... 경로가 있으면 퍼블릭, 없으면 프라이빗. 인스턴스가 실제로 인터넷과 통신하려면 퍼블릭 IP(또는 탄력적 IP)도 있어야 한다. 보안 그룹은 허용 규칙일 뿐 길을 만들지 않는다.

NAT

프라이빗 서버의 바깥 연결

프라이빗 서브넷의 서버가 외부 패키지 저장소에는 나가야 하지만, 인터넷에서 들어오는 연결은 막고 싶다.

  • 퍼블릭 서브넷의 NAT 게이트웨이로 나가게 한다
  • 프라이빗 라우팅에 인터넷 게이트웨이를 잇는다
  • 서버에 퍼블릭 IP를 붙여 직접 나간다
  • 서버 보안 그룹의 인바운드를 모두 연다
  • NAT 게이트웨이가 퍼블릭 서브넷에 있어야 해서
  • NAT 게이트웨이에 보안 그룹을 붙이지 않아서
  • 서버 보안 그룹의 아웃바운드가 기본값이라서
  • 프라이빗 서브넷에는 라우팅 테이블이 없어서

NAT 게이트웨이에는 보안 그룹이 없다. NAT 게이트웨이는 안에서 시작한 연결만 밖으로 내보내고, 밖에서 먼저 들어오는 연결은 받지 않는다. 자신은 인터넷 게이트웨이로 나가야 하므로 퍼블릭 서브넷에 있어야 하고, 프라이빗 서브넷의 라우팅 테이블이 0.0.0.0/0 → nat-...을 가리켜야 한다.

라우팅

프라이빗 서버가 인터넷에 나가는 길

프라이빗 서브넷의 서버가 외부 API를 부를 때 패킷이 지나가는 순서대로 놓으세요.

  1. 프라이빗 서브넷의 서버
  2. 프라이빗 라우팅 테이블 (0.0.0.0/0 → NAT)
  3. 퍼블릭 서브넷의 NAT 게이트웨이
  4. 인터넷 게이트웨이
  5. 인터넷

NAT 게이트웨이가 출발지 주소를 자기 주소로 바꿔 내보내고, 돌아온 응답을 다시 서버에 전달한다. 그래서 바깥에서는 서버 주소가 보이지 않는다.

서브넷

서브넷에서 쓸 수 있는 IP

10.0.1.0/24 서브넷에서 인스턴스에 줄 수 있는 IP는 몇 개일까?

  • 251개
  • 256개
  • 254개
  • 255개

/24는 256개지만 AWS는 서브넷마다 5개를 예약한다: 네트워크 주소(.0), VPC 라우터(.1), DNS(.2), 예비(.3), 브로드캐스트(.255). 그래서 251개. 작은 서브넷(/28 = 16개)에서는 11개만 남아서 금방 모자란다.

보안 그룹

보안 그룹과 응답 트래픽

보안 그룹에 인바운드 443만 허용하고 아웃바운드 규칙은 모두 지웠다. 클라이언트의 HTTPS 요청에 대한 응답은?

  • 나간다. 보안 그룹은 상태를 기억해 응답을 자동으로 허용한다
  • 막힌다. 아웃바운드 규칙이 없어서
  • 응답 포트(1024~65535)를 아웃바운드로 열어야 나간다
  • NACL이 허용할 때만 나간다

보안 그룹은 상태 저장(stateful)이라 허용해서 들어온 연결의 응답은 규칙과 상관없이 나간다. 아웃바운드 규칙은 인스턴스가 먼저 시작하는 연결(예: 외부 API 호출)에만 적용된다.

NACL

NACL과 응답 트래픽

서브넷의 NACL에 인바운드 443만 허용하고 아웃바운드는 기본 Deny뿐이다. HTTPS 응답은?

  • 막힌다. 응답용 임시 포트를 아웃바운드로 열어야 한다
  • 나간다. 응답은 항상 자동으로 허용된다
  • 보안 그룹이 허용하면 나간다
  • 443 응답은 443 포트로 나가므로 나간다

NACL은 상태 비저장(stateless)이라 들어온 요청과 나가는 응답을 따로 검사한다. 응답은 클라이언트의 임시 포트(보통 1024~65535)로 가므로 아웃바운드에 그 범위를 허용해야 한다. 보안 그룹과 NACL을 둘 다 통과해야 한다.

NACL

IP 하나만 막기

공격하는 IP 하나만 서브넷 단위로 막고 싶다. 무엇을 쓸까?

  • NACL에 그 IP의 Deny 규칙
  • 보안 그룹에 그 IP의 Deny 규칙
  • 라우팅 테이블에서 그 IP를 지운다
  • 인터넷 게이트웨이를 분리한다
  • 허용된다. 작은 번호의 규칙이 먼저 적용된다
  • 거부된다. NACL에서도 Deny가 항상 이긴다
  • 거부된다. IP를 콕 집은 규칙이 이긴다
  • 두 규칙이 충돌해 트래픽이 모두 막힌다

보안 그룹은 Allow 규칙만 있어서 특정 IP를 막을 수 없다. NACL은 Allow와 Deny가 있고, 규칙을 번호가 작은 것부터 보다가 처음 맞는 규칙을 적용한다. 그래서 막을 규칙은 "모두 허용"보다 작은 번호로 넣는다. (IAM의 "Deny가 이긴다"와 헷갈리기 쉽다.)

보안 그룹

DB 접근을 웹 서버로만

웹 서버들만 DB의 3306 포트에 접속하게 하는 가장 좋은 방법은?

  • DB 보안 그룹 인바운드 소스로 웹 서버의 보안 그룹을 지정한다
  • 웹 서버의 IP를 하나씩 인바운드에 적는다
  • 인바운드 소스를 0.0.0.0/0으로 두고 DB 비밀번호로 막는다
  • NACL에 웹 서버 IP를 적는다

보안 그룹 규칙의 소스로 다른 보안 그룹을 지정하면 그 그룹이 붙은 인스턴스만 허용된다. 웹 서버가 오토 스케일링으로 늘거나 IP가 바뀌어도 규칙을 고칠 필요가 없다.

VPC 연결

세 VPC 잇기

VPC A–B, B–C가 각각 피어링돼 있다. A의 서버가 C의 서버에 접속하면?

  • 안 된다. A–C를 따로 피어링해야 한다
  • 된다. B를 거쳐 자동으로 전달된다
  • 된다. 세 VPC가 같은 리전이면
  • 된다. A 라우팅에 C를 B 경유로 적으면

VPC 피어링은 두 VPC 사이의 직접 연결일 뿐이고, B를 지나 C로 가는 경로를 만들 수 없다(전이 불가). VPC가 많아지면 모두 서로 잇는 대신 Transit Gateway 같은 허브를 쓴다.

VPC 엔드포인트

NAT 없이 S3 쓰기

프라이빗 서브넷의 서버가 NAT 게이트웨이를 거치지 않고, 추가 요금 없이 S3에 접근하게 하려면?

  • S3 게이트웨이 VPC 엔드포인트
  • S3 인터페이스 VPC 엔드포인트
  • 서버에 퍼블릭 IP를 붙인다
  • S3 버킷과 VPC를 피어링한다

게이트웨이 엔드포인트는 S3와 DynamoDB에만 있고 추가 요금이 없다. 라우팅 테이블에 경로가 추가되어 트래픽이 AWS 내부로 간다. 인터페이스 엔드포인트(PrivateLink)는 대부분의 서비스를 지원하지만 시간·데이터 요금이 있다. S3와 대량으로 주고받으면 NAT 처리 요금이 크게 줄어든다.

Route 53

루트 도메인 연결

example.com(서브도메인 없는 루트 도메인)을 CloudFront 배포로 연결하려면 Route 53에서 무엇을 만들까?

  • 별칭(Alias) A 레코드
  • CNAME 레코드
  • MX 레코드
  • TXT 레코드

DNS 규칙상 루트 도메인(zone apex)에는 CNAME을 만들 수 없다. Route 53의 별칭 레코드는 A 레코드처럼 동작하면서 CloudFront, ALB, S3 웹사이트 같은 AWS 리소스를 가리킬 수 있고, AWS 리소스로 가는 별칭 조회는 요금도 받지 않는다. www 같은 서브도메인은 CNAME도 된다.

로드 밸런서

로드 밸런서 고르기

/api는 API 서버로, /images는 이미지 서버로 경로에 따라 나눠 보내고 싶다.

  • Application Load Balancer
  • Network Load Balancer
  • Gateway Load Balancer
  • Route 53 가중치 레코드
  • Network Load Balancer
  • Application Load Balancer
  • Gateway Load Balancer
  • CloudFront

ALB는 7계층(HTTP·HTTPS)이라 경로, 호스트, 헤더를 보고 나눠 보낸다. NLB는 4계층(TCP·UDP·TLS)이라 내용은 보지 않고 매우 빠르며, AZ마다 고정 IP(탄력적 IP)를 줄 수 있다. Gateway LB는 방화벽 같은 네트워크 장비를 끼워 넣을 때 쓴다.

PART 3

EC2 · Lambda · 컨테이너

서버를 어떻게 사고, 어디에 데이터를 두고, Lambda가 어떻게 재사용되는지처럼 비용과 장애로 바로 이어지는 선택을 다룹니다.

구매 옵션

가장 싸게 돌리기

밤새 도는 배치 작업이 중간에 끊겨도 다시 이어서 할 수 있다. 가장 싸게 돌리려면?

  • 스팟 인스턴스
  • 온디맨드 인스턴스
  • 전용 호스트
  • 예약 인스턴스 3년
  • 2분 전 중단 알림
  • 24시간 전 이메일
  • 알림 없이 바로 종료
  • 1시간 전 콘솔 알림

스팟은 남는 용량을 크게 할인해서 쓰는 대신, AWS가 용량이 필요하면 2분 전 알림 후 회수한다. 그래서 중단돼도 괜찮은 작업(배치, CI, 이미지 변환)에 쓰고, 알림을 받으면 작업 상태를 저장한다. 1년 이상 꾸준히 도는 서버는 Savings Plans나 예약 인스턴스가 싸다.

스토리지

인스턴스 스토어의 데이터

인스턴스 스토어에 저장한 파일은 인스턴스를 중지했다가 다시 시작하면?

  • 사라진다
  • 그대로 남는다
  • 자동으로 EBS 스냅샷에 백업된다
  • 중지 전에 저장한 파일만 남는다
  • 그대로 남는다
  • 사라진다
  • 미리 스냅샷을 찍어 둔 것만 남는다
  • 루트 볼륨일 때만 남는다

인스턴스 스토어는 호스트 서버에 붙은 디스크라 매우 빠르지만 임시다. 재부팅에서는 남지만, 중지·최대 절전·종료하면 데이터가 사라진다(다른 호스트로 옮겨질 수 있어서). 남아야 하는 데이터는 EBS나 S3에 둔다.

EBS

다른 AZ로 볼륨 옮기기

ap-northeast-2a에 있는 EBS 볼륨을 2c의 EC2에 붙이려면?

  • 스냅샷을 만들어 2c에서 새 볼륨으로 복원한다
  • 분리(detach)한 뒤 2c 인스턴스에 바로 붙인다
  • 같은 리전이라 그냥 붙일 수 있다
  • 볼륨 유형을 io2로 바꾸면 붙는다

EBS 볼륨은 만들어진 가용 영역(AZ)에 묶여 있어서 같은 AZ의 인스턴스에만 붙는다. 다른 AZ로 옮기려면 스냅샷(S3에 저장돼 리전 전체에서 쓸 수 있음)으로 새 볼륨을 만든다. 여러 AZ에서 같은 파일을 봐야 하면 EFS를 쓴다.

오토 스케일링

고장 난 서버가 안 바뀔 때

ALB 뒤의 오토 스케일링 그룹에서 앱이 계속 500만 내는데 인스턴스가 교체되지 않는다. 가장 흔한 원인은?

  • ELB 상태 검사를 켜지 않아서 (기본은 EC2 검사)
  • ALB 헬스 체크는 500을 정상으로 봐서
  • 오토 스케일링은 하루에 한 번만 검사해서
  • 최소 용량이 1이라 교체할 여유가 없어서

오토 스케일링 그룹은 기본으로 EC2 상태 검사(하드웨어·OS가 살아 있나)만 본다. 앱이 망가져도 OS는 살아 있으면 정상이다. ELB 상태 검사를 켜면 로드 밸런서의 헬스 체크(예: /health가 200인지)에 실패한 인스턴스를 교체한다.

Lambda

오래 걸리는 작업

20분 걸리는 영상 변환을 Lambda 하나로 처리하려 한다. 어떻게 될까?

  • 안 된다. 최대 실행 시간이 15분이다
  • 된다. 타임아웃을 20분으로 설정하면
  • 된다. 메모리를 늘리면 제한도 늘어난다
  • 된다. 비동기로 호출하면 제한이 없다

Lambda 한 번의 실행은 최대 900초(15분)다. 더 긴 작업은 잘게 나눠 Step Functions로 잇거나, 컨테이너(ECS Fargate)나 AWS Batch로 돌린다. 메모리를 늘리면 CPU도 늘어 빨라질 수는 있지만 시간 제한 자체는 그대로다.

Lambda

핸들러 밖의 코드

const db = createConnection(); // 핸들러 밖

export const handler = async (event) => {
  return db.query('SELECT 1');
};

핸들러 밖에서 만든 DB 연결 db는 어떻게 될까?

  • 실행 환경이 재사용되면 다음 호출에서도 그대로 쓰인다
  • 호출마다 새로 만들어진다
  • Lambda가 핸들러 밖 코드를 실행하지 않는다
  • 첫 호출이 끝나면 항상 버려진다

Lambda는 호출이 끝난 실행 환경을 한동안 살려 두고 다음 호출에 재사용한다(웜 스타트). 핸들러 밖 코드는 환경이 처음 만들어질 때 한 번만 실행되므로 SDK 클라이언트, DB 연결을 여기서 만들면 호출마다 다시 만들지 않아도 된다. 대신 요청마다 달라야 하는 값을 여기 두면 다른 요청에 섞인다.

Lambda

동시성 설정

첫 요청이 느린 콜드 스타트를 줄이려고 실행 환경을 미리 준비해 두는 설정은?

  • 프로비저닝된 동시성
  • 예약된 동시성
  • 타임아웃 늘리기
  • 메모리 줄이기
  • 예약된 동시성
  • 프로비저닝된 동시성
  • 타임아웃 늘리기
  • SQS 배치 크기 늘리기

예약된 동시성: 이 함수 몫으로 떼어 두는 개수. 보장이면서 동시에 상한이다(DB가 버틸 만큼만 돌리게 할 때도 쓴다). 프로비저닝된 동시성: 실행 환경을 미리 초기화해 두어 콜드 스타트를 없앤다(켜 둔 시간만큼 요금).

Lambda

비동기 호출에서 난 에러

S3 이벤트처럼 비동기로 호출된 Lambda가 에러를 던지면?

  • Lambda가 기본으로 두 번 더 재시도한다
  • 재시도 없이 이벤트가 사라진다
  • 성공할 때까지 무한히 재시도한다
  • 에러가 S3로 돌아가 업로드가 취소된다

비동기 호출은 Lambda가 내부 큐에 넣고 실행하며, 함수 에러가 나면 기본 2번 더 재시도한다(재시도 횟수·최대 이벤트 나이는 설정 가능). 그래서 같은 이벤트가 여러 번 처리될 수 있으니 함수는 멱등하게 짜고, 끝까지 실패한 이벤트는 실패 대상(SQS·SNS)이나 DLQ로 보낸다.

컨테이너

서버 없이 컨테이너 돌리기

EC2 서버를 만들고 패치하는 일 없이 컨테이너만 돌리고 싶다.

  • ECS on Fargate
  • ECS on EC2
  • EC2에 Docker를 직접 설치
  • EKS 관리형 노드 그룹

Fargate는 컨테이너가 돌 서버를 AWS가 관리해서, 작업(Task)에 CPU·메모리만 정해 주면 된다. ECS on EC2나 EKS 노드 그룹은 컨테이너를 올릴 EC2 인스턴스를 직접 두고 관리해야 한다. 대신 Fargate는 같은 자원이면 보통 더 비싸다.

PART 4

S3

버킷을 비공개로 지키면서 필요한 사람에게만 파일을 주는 법, 저장 클래스와 요금의 함정, 브라우저에서 바로 올리기를 다룹니다.

공개 설정

버킷 정책을 넣어도 403

Principal "*"에 s3:GetObject를 허용하는 버킷 정책을 저장하려는데 거부되거나, 저장돼도 여전히 403이다. 가장 흔한 원인은?

  • 퍼블릭 액세스 차단이 켜져 있어서
  • 객체 ACL을 public-read로 안 바꿔서
  • 버킷에 CORS 설정이 없어서
  • 버킷과 요청의 리전이 달라서

새 버킷은 기본으로 퍼블릭 액세스 차단이 켜져 있어서 공개 정책을 막거나 무시한다. 또 새 버킷은 ACL이 꺼져 있어(객체 소유권: 버킷 소유자 적용) 객체 ACL로 공개할 수도 없다. 정말 공개가 필요하면 차단을 풀어야 하지만, 웹사이트라면 보통 버킷은 비공개로 두고 CloudFront(OAC)로 연다.

일관성

덮어쓴 직후 읽기

같은 키로 새 파일을 PUT한 직후 GET하면?

  • 항상 새 파일을 받는다
  • 몇 초 동안은 옛 파일을 받을 수 있다
  • 잠깐 404가 난다
  • 리전마다 다르다

S3는 2020년 12월부터 모든 리전에서 객체 PUT·DELETE에 강한 읽기 후 쓰기 일관성을 자동으로 제공한다. 쓰기가 성공하면 바로 뒤의 읽기·목록 조회에 반영된다. "S3는 최종적 일관성이라 잠깐 옛 값이 보인다"는 예전 이야기다. (CloudFront 같은 캐시 앞단은 별개다.)

저장 클래스

저장 클래스와 요금

S3 Standard-IA에 파일을 올리고 10일 뒤 지웠다. 저장 요금은?

  • 30일 치가 청구된다
  • 10일 치만 청구된다
  • 지웠으니 청구되지 않는다
  • 90일 치가 청구된다
  • S3 Glacier Deep Archive
  • S3 Standard-IA
  • S3 Intelligent-Tiering
  • S3 Standard

IA와 Glacier 계열은 저장 단가가 싼 대신 최소 저장 기간이 있다(Standard-IA 30일, Glacier Instant·Flexible 90일, Deep Archive 180일). 그보다 일찍 지우거나 옮기면 남은 기간이 청구된다. 또 꺼낼 때 검색 요금이 붙는다. 자주 바뀌거나 금방 지울 파일은 Standard가 오히려 싸다.

접근 제어

비공개 파일을 잠깐 주기

버킷은 비공개로 두고, 로그인한 사용자만 특정 파일을 10분 동안 내려받게 하고 싶다.

  • 만료 10분짜리 presigned URL을 만들어 준다
  • 버킷을 공개하고 파일 이름을 어렵게 짓는다
  • 파일을 10분만 공개로 바꿨다가 되돌린다
  • 사용자마다 IAM 사용자를 만들어 준다
  • 역할의 임시 자격 증명이 만료돼서
  • presigned URL은 최대 1시간이라서
  • EC2를 재부팅해서 URL이 취소돼서
  • 다른 사용자가 URL을 먼저 써서

presigned URL은 만든 사람의 권한으로 서명한 링크라, 받은 사람은 AWS 계정 없이도 정해진 시간 동안 그 작업(GET·PUT)을 할 수 있다. 최대 유효 기간은 7일이지만, 임시 자격 증명(역할)으로 만들면 그 자격 증명이 끝날 때 URL도 끝난다. 오래 가는 링크가 필요하면 CloudFront 서명 URL 같은 방법을 쓴다.

브라우저 업로드

브라우저에서 바로 올릴 때

웹 페이지(https://app.example.com)에서 presigned URL로 S3에 PUT하는데 브라우저에 CORS 에러가 난다. 고칠 곳은?

  • 버킷의 CORS 설정에 사이트 출처와 PUT을 허용한다
  • IAM 정책에 s3:PutCors 권한을 준다
  • presigned URL을 다시 만든다
  • CloudFront 캐시를 무효화한다

브라우저가 다른 출처(버킷 도메인)로 PUT하면 CORS 규칙이 적용되고, 응답 헤더를 주는 쪽은 S3 버킷이다. 버킷의 CORS 설정에 AllowedOrigins(사이트 주소), AllowedMethods(PUT), 필요한 AllowedHeaders를 넣는다. 서버를 거치지 않고 큰 파일을 올릴 때 흔히 쓰는 구조다.

버전 관리

버전 관리 버킷에서 지우기

버전 관리를 켠 버킷에서 버전 ID 없이 객체를 DELETE하면?

  • 삭제 마커가 생기고 이전 버전은 남는다
  • 모든 버전이 영구 삭제된다
  • 버전 관리가 자동으로 꺼진다
  • 휴지통으로 가서 30일 뒤 지워진다
  • 끌 수는 없고 일시 중지만 할 수 있다
  • 언제든 끌 수 있다
  • 버킷을 비워야 끌 수 있다
  • 지원 센터에 요청해야 끌 수 있다

버전 관리 버킷에서 그냥 지우면 객체 위에 삭제 마커가 덮일 뿐이라, 마커를 지우면 되살릴 수 있다(실수 복구). 대신 옛 버전도 저장 요금이 계속 나가니 수명 주기 규칙으로 정리한다. 버전 관리는 한 번 켜면 일시 중지만 가능하다.

업로드

큰 파일 올리기

3GB 영상을 S3에 올린다. AWS가 권장하는 방법은?

  • 멀티파트 업로드
  • 5GB 이하이니 단일 PUT 한 번
  • 압축해서 단일 PUT
  • Base64로 바꿔 JSON 본문에 담아 올린다

단일 PUT은 5GB까지 되지만, AWS는 100MB 이상이면 멀티파트 업로드를 권장한다. 여러 조각을 동시에 올려 빠르고, 한 조각이 실패하면 그 조각만 다시 올린다. 끝나지 않은 멀티파트 조각도 요금이 나가니 수명 주기 규칙으로 정리한다.

수명 주기

로그 자동 정리

코드를 짜지 않고, 30일 지난 로그는 Standard-IA로 옮기고 1년 지나면 자동으로 지우고 싶다.

  • S3 수명 주기(Lifecycle) 규칙
  • 매일 도는 Lambda 크론
  • S3 Intelligent-Tiering
  • 버킷 버전 관리

수명 주기 규칙으로 접두사·태그별로 "며칠 뒤 다른 클래스로 전환", "며칠 뒤 삭제", "옛 버전·미완료 멀티파트 정리"를 코드 없이 걸 수 있다. Intelligent-Tiering은 접근 빈도에 따라 클래스를 알아서 옮기지만 지워 주지는 않는다.

PART 5

CloudFront · 배포

S3 + CloudFront로 프론트엔드를 배포할 때 실제로 부딪히는 것들입니다. 버킷을 비공개로 두기, 인증서, SPA 새로고침 에러, 캐시와 무효화.

요청 흐름

정적 사이트 요청이 가는 길

사용자가 https://example.com을 열 때 요청이 지나가는 순서대로 놓으세요.

  1. 브라우저
  2. Route 53 (DNS 조회)
  3. CloudFront 엣지 (캐시 확인)
  4. S3 버킷 (캐시에 없을 때)

DNS가 가장 가까운 CloudFront 엣지 주소를 알려 주고, 엣지에 캐시가 있으면 S3까지 가지 않고 바로 응답한다. 캐시가 없을 때만 오리진(S3)에서 가져와 캐시한다.

오리진 보호

버킷은 비공개로, 사이트는 공개로

S3 버킷은 비공개로 두고, CloudFront를 통해서만 사이트가 보이게 하고 싶다.

  • OAC를 쓰고 버킷 정책에 CloudFront만 허용한다
  • 버킷을 공개로 열고 CloudFront를 앞에 둔다
  • S3 웹사이트 엔드포인트를 공개 오리진으로 쓴다
  • 모든 파일에 presigned URL을 붙인다

OAC는 CloudFront가 서명한 요청으로 S3에 접근하게 하고, 버킷 정책은 서비스 주체 cloudfront.amazonaws.com을 그 배포의 ARN(AWS:SourceArn)일 때만 허용한다. 그러면 S3 주소로 직접 들어오는 요청은 막힌다. 예전 방식인 OAI보다 OAC가 권장된다.

인증서

CloudFront용 인증서

서울 리전 ACM에서 인증서를 만들었는데 CloudFront 설정의 인증서 목록에 나오지 않는다. 이유는?

  • CloudFront용 인증서는 us-east-1에 있어야 해서
  • 새 인증서는 24시간 뒤에야 목록에 보여서
  • CloudFront는 ACM 인증서를 아예 못 써서
  • 와일드카드 인증서만 쓸 수 있어서

CloudFront는 전 세계 엣지에서 도는 글로벌 서비스라, ACM 인증서를 us-east-1에서 만들거나 가져와야 한다. 서울 리전 인증서는 같은 리전의 ALB 같은 곳에 쓴다. 처음 배포할 때 가장 많이 막히는 지점이다.

SPA

새로고침하면 에러

React SPA를 S3 + CloudFront(OAC)에 올렸다. 첫 화면은 되는데 /settings에서 새로고침하면 AccessDenied(403)가 뜬다. 해결은?

  • 403·404 오류 응답을 /index.html(200)로 바꾼다
  • CloudFront 캐시를 /*로 전부 무효화한다
  • 버킷 CORS 설정에 GET 요청을 허용한다
  • 버킷 정책에 s3:ListBucket을 허용한다
  • ListBucket 권한이 없으면 S3가 403을 줘서
  • CloudFront가 404를 403으로 바꿔서
  • OAC가 GetObject를 허용하지 않아서
  • 버킷의 퍼블릭 액세스 차단 때문에

브라우저가 /settings를 요청하면 S3에는 settings라는 객체가 없다. 라우팅은 JS가 하므로 어떤 경로든 index.html을 돌려주면 된다: CloudFront의 사용자 지정 오류 응답(403, 404 → /index.html, 응답 코드 200)이나 CloudFront Functions로 경로를 바꾼다. S3는 목록 권한이 없는 요청자에게 "없다"는 정보를 주지 않으려고 403을 준다.

캐시

배포했는데 옛 화면

새 버전을 S3에 올렸는데 사용자에게 한동안 옛 화면이 보인다. 가장 가능성 높은 원인은?

  • CloudFront 엣지에 옛 파일이 남아서
  • S3가 최종적 일관성이라 옛 파일을 줘서
  • S3 버전 관리가 옛 버전을 돌려줘서
  • 새 파일이 다른 리전으로 복제되는 중이라서
  • 1개
  • 파일 수만큼
  • 폴더 수만큼
  • 무효화는 항상 무료다

CloudFront는 TTL 동안 엣지에 캐시한 파일을 준다. 배포 뒤에는 무효화(Invalidation)로 지우거나, 애초에 index.html은 짧게 캐시한다. 무효화는 매달 1,000개 경로까지 무료이고 /* 같은 와일드카드는 경로 1개로 친다. 해시가 붙은 JS·CSS는 이름이 바뀌므로 무효화할 필요가 없다.

캐시

CloudFront는 얼마나 캐시할까

S3 객체에 Cache-Control: max-age=60이 있고, 캐시 정책은 최소 TTL 0초·최대 TTL 1년이다. CloudFront는 이 객체를 얼마나 캐시할까?

  • 60초
  • 1년
  • 0초
  • 24시간

CloudFront는 오리진의 Cache-Control: max-age를 따르되, 캐시 정책의 최소·최대 TTL 범위 안으로 맞춘다. 60초는 0초~1년 안이라 그대로 60초. 오리진이 헤더를 주지 않으면 기본 TTL(보통 24시간)을 쓴다. 그래서 배포 파일별로 S3에 Cache-Control을 달아 두면 제어하기 쉽다.

캐시

캐시 적중률이 낮을 때

CloudFront 캐시 적중률이 유난히 낮다. 원인이 될 수 있는 설정은?

  • 캐시 키에 모든 쿼리 문자열과 쿠키를 넣었다
  • TTL을 길게 잡았다
  • gzip·brotli 압축을 켰다
  • 오리진을 OAC로 보호했다

캐시 키에 들어가는 값이 다르면 다른 파일로 따로 캐시된다. 쿼리 문자열(utm 태그 등)이나 쿠키를 모두 키에 넣으면 사실상 요청마다 다른 키가 되어 오리진까지 간다. 내용에 영향을 주는 값만 캐시 키에 넣고, 오리진에 전달만 할 값은 오리진 요청 정책으로 따로 보낸다.

엣지 컴퓨팅

엣지에서 코드 돌리기

모든 요청에서 /about 같은 경로를 /about/index.html로 바꾸는 가벼운 처리를 엣지에서 하고 싶다.

  • CloudFront Functions
  • Lambda@Edge
  • ALB 리스너 규칙
  • S3 리다이렉트 규칙
  • Lambda@Edge
  • CloudFront Functions
  • S3 버킷 정책
  • Route 53 상태 검사

CloudFront Functions: 뷰어 요청·응답 단계에서만, JavaScript로, 1밀리초 안쪽의 가벼운 처리(URL 바꾸기, 헤더 붙이기). 네트워크 호출은 못 한다. Lambda@Edge: 오리진 요청·응답 단계도 되고 네트워크 호출, 긴 처리가 가능하지만 더 느리고 비싸다.

PART 6

DB · 메시징

RDS의 Multi-AZ와 복제본, DynamoDB의 일관성과 파티션, SQS의 중복과 순서처럼 "왜 데이터가 이상하지?"의 원인이 되는 것들입니다.

RDS

RDS 읽기 나누기

RDS Multi-AZ(인스턴스 배포)의 대기 인스턴스로 읽기 쿼리를 나눌 수 있을까?

  • 없다. 대기 인스턴스는 읽기를 받지 않는다
  • 있다. 대기 인스턴스 주소로 읽으면 된다
  • 있다. RDS가 읽기를 자동으로 나눠 준다
  • 있다. 장애 조치 중에만 못 읽는다
  • 읽기 전용 복제본으로 조회를 보낸다
  • Multi-AZ를 켜서 대기로 읽기를 나눈다
  • 인스턴스를 다른 AZ로 옮긴다
  • 자동 백업을 더 자주 하게 한다

Multi-AZ(인스턴스 배포)는 다른 AZ에 동기 복제한 대기 인스턴스를 두고, 주 DB가 죽으면 자동으로 넘긴다. 목적은 가용성이라 대기 인스턴스는 읽기를 받지 않는다. 읽기 전용 복제본은 비동기 복제로 읽기를 나누는 용도다. (두 개의 읽기 가능한 대기를 두는 Multi-AZ DB 클러스터 배포는 별도 방식이다.)

RDS

장애 조치 후 연결

Multi-AZ에서 장애 조치가 일어났다. 앱의 DB 연결 주소는?

  • 그대로 둔다. 같은 엔드포인트가 새 주 DB로
  • 새 주 DB의 IP로 바꿔야 한다
  • 대기 인스턴스의 엔드포인트로 바꿔야 한다
  • 앱도 새 AZ로 옮겨 다시 배포해야 한다

RDS는 장애 조치 때 같은 엔드포인트(DNS 이름)가 새 주 DB를 가리키게 바꾼다. 그래서 앱은 IP가 아니라 엔드포인트로 접속하고, DNS를 너무 오래 캐시하지 않으며, 끊긴 연결을 다시 맺는 재시도 로직을 둔다.

RDS

복제본에서 방금 쓴 데이터

주 DB에 글을 쓴 직후 읽기 복제본에서 조회했더니 새 글이 없다. 이유는?

  • 복제본은 비동기라 잠깐 늦을 수 있어서
  • 트랜잭션이 아직 커밋되지 않아서
  • 복제본은 1시간마다 스냅샷으로 맞춰져서
  • 복제본은 조회 결과를 캐시해 두어서

읽기 복제본은 비동기 복제라 복제 지연(replica lag)만큼 늦다. "쓰고 바로 내 글 보기"처럼 방금 쓴 값을 꼭 봐야 하는 조회는 주 DB에서 읽는다.

DynamoDB

DynamoDB의 기본 읽기

DynamoDB에서 옵션 없이 GetItem을 하면 읽기 방식은?

  • 최종적 일관성
  • 강한 일관성
  • 트랜잭션 읽기
  • 테이블을 만들 때 고른 방식
  • 지원되지 않는다
  • 테이블과 똑같이 된다
  • 요금이 두 배로 된다
  • 파티션 키가 같을 때만 된다

DynamoDB 읽기는 기본이 최종적 일관성이고, ConsistentRead: true로 강한 일관성을 고를 수 있다(읽기 용량을 두 배 쓴다). 다만 GSI는 비동기로 갱신되어 강한 일관성 읽기를 지원하지 않는다.

DynamoDB

쓰기가 스로틀될 때

주문 테이블의 파티션 키를 주문 날짜(2026-09-24)로 했더니, 오늘 주문이 몰릴 때 쓰기가 스로틀된다. 원인은?

  • 한 파티션 키로 쓰기가 몰려서 (핫 파티션)
  • 하루 쓰기 횟수 한도에 걸려서
  • 정렬 키를 정하지 않아서
  • 온디맨드 모드는 쓰기가 느려서

DynamoDB는 파티션 키로 데이터를 나눠 저장하고, 파티션마다 처리량 한계가 있다. 날짜처럼 값의 종류가 적고 한쪽으로 몰리는 키는 그날의 모든 쓰기가 한 파티션에 몰린다. 주문 ID·사용자 ID처럼 고르게 퍼지는 키를 쓰거나 키에 무작위 접미사를 붙인다.

SQS

처리 시간과 가시성 제한

워커가 메시지 하나를 처리하는 데 60초가 걸리는데, 큐의 가시성 제한 시간은 기본값 30초다. 무슨 일이 생길까?

  • 처리 중인 메시지를 다른 워커가 또 받는다
  • 30초가 지나면 메시지가 삭제된다
  • 처리하는 동안 제한 시간이 자동으로 늘어난다
  • 60초 동안 다음 메시지를 받을 수 없다

SQS는 메시지를 받아 간 뒤 가시성 제한 시간 동안만 숨긴다. 그 안에 DeleteMessage를 하지 않으면 다시 보여서 다른 소비자가 받는다. 처리 시간보다 넉넉하게(기본 30초, 최대 12시간) 잡거나, 처리 중에 ChangeMessageVisibility로 늘린다.

SQS

큐 종류 고르기

SQS 표준 큐의 소비자가 대비해야 하는 것은?

  • 같은 메시지가 두 번 이상 올 수 있다
  • 메시지가 사라질 수 있다
  • 메시지 하나에 소비자가 하나로 고정된다
  • 메시지가 항상 순서대로 온다
  • FIFO 큐 (주문 ID를 메시지 그룹 ID로)
  • 표준 큐 (소비자를 한 개만 둔다)
  • 표준 큐 (메시지에 순번을 붙인다)
  • 표준 큐 + DLQ (실패는 따로 모은다)

표준 큐: 처리량이 매우 크지만 최소 한 번 전달(가끔 중복)이고 순서는 최선일 뿐이다. 그래서 소비자를 멱등하게 만든다. FIFO 큐: 같은 메시지 그룹 안에서 순서를 지키고 정확히 한 번 처리한다.

SQS

계속 실패하는 메시지

형식이 잘못돼 처리할 때마다 실패하는 메시지가 큐에서 계속 재시도되며 비용과 로그를 먹는다.

  • 최대 수신 횟수를 정해 DLQ로 보낸다
  • 가시성 제한 시간을 0으로 줄인다
  • 큐를 FIFO 큐로 바꾼다
  • 소비자 워커를 더 늘린다

재드라이브 정책에 maxReceiveCount를 정하면, 그 횟수만큼 받아 갔는데도 지워지지 않은 메시지를 DLQ로 옮긴다. 정상 메시지 처리를 막지 않고, 실패한 메시지는 따로 살펴보거나 고친 뒤 다시 보낼 수 있다.

SNS

하나의 이벤트를 여러 곳에

주문이 들어오면 결제·알림·분석 서비스가 각자 같은 이벤트를 받아 따로 처리해야 한다.

  • SNS 토픽에 서비스별 SQS 큐를 구독시킨다
  • SQS 큐 하나를 세 서비스가 같이 읽는다
  • SQS FIFO 큐 하나를 세 서비스가 같이 읽는다
  • SQS 큐 하나에 소비자 그룹을 세 개 만든다

SQS 큐 하나를 여러 소비자가 읽으면 메시지 하나를 한 소비자만 가져간다(일을 나눠 가짐). 모두가 받아야 하면 SNS 토픽 → 여러 SQS 큐(팬아웃)로 복사해서 보낸다. 서비스마다 자기 큐가 있어 속도도, 장애도 서로 영향을 덜 준다.

공동 책임

누가 패치할까

EC2 인스턴스의 운영체제 보안 패치는 누구 책임일까?

  • 고객
  • AWS
  • Systems Manager를 켜면 AWS
  • AMI를 만든 회사
  • AWS가 한다 (고객은 유지 관리 시간대를 정한다)
  • 고객이 DB 서버에 SSH로 접속해 한다
  • 고객이 새 인스턴스로 옮겨 가며 한다
  • AWS Support에 요청할 때만 된다

공동 책임 모델: AWS는 클라우드 자체(데이터 센터, 하드웨어, 가상화)를, 고객은 클라우드 안에서 만든 것(데이터, IAM, 보안 그룹, EC2의 OS·앱)을 책임진다. 관리형 서비스일수록 AWS 몫이 커진다. Systems Manager 패치 관리자는 고객이 쓰는 도구라 켜도 책임은 고객에게 있다. RDS는 AWS가 엔진·OS를 패치하지만 DB 사용자 권한과 데이터 보호는 여전히 고객 몫이다.

감사

누가 바꿨는지 찾기

어제 누군가 보안 그룹에서 22번 포트를 전체 공개로 열었다. 누가 언제 했는지 알려면?

  • CloudTrail 이벤트 기록
  • CloudWatch CPU 지표
  • VPC 흐름 로그
  • Trusted Advisor

CloudTrail은 계정에서 일어난 API 호출(AuthorizeSecurityGroupIngress 같은)을 누가, 언제, 어디서 했는지 기록한다. CloudWatch는 지표·로그·경보, VPC 흐름 로그는 오간 네트워크 트래픽이라 "누가 설정을 바꿨나"는 알 수 없다.

모니터링

CPU가 높으면 알림

EC2 CPU 사용률이 5분 동안 80%를 넘으면 메일을 받고 싶다.

  • CloudWatch 경보 + SNS 메일
  • EC2 상태 검사 알림
  • AWS Health Dashboard 알림
  • CloudTrail 이벤트 알림

CloudWatch 경보는 지표가 임계값을 정한 기간 동안 넘으면 상태가 바뀌고, SNS로 메일·문자를 보내거나 오토 스케일링을 움직인다. EC2 상태 검사는 인스턴스가 살아 있는지만, Health Dashboard는 AWS 쪽 장애만 알린다. 메모리·디스크 사용률은 기본 지표에 없어서 CloudWatch 에이전트를 설치해야 한다.

비용

요금 폭탄 막기

이번 달 예상 요금이 100달러를 넘을 것 같으면 미리 메일을 받고 싶다.

  • AWS Budgets의 예측 비용 알림
  • CloudWatch 결제 경보(누적 청구액)
  • Cost Explorer 비용 그래프
  • CloudTrail 결제 API 기록

AWS Budgets는 실제 비용뿐 아니라 예측 비용이 기준을 넘을 때도 알린다. CloudWatch 결제 경보는 이미 쌓인 청구액 기준이라 "넘을 것 같으면"은 못 잡고, Cost Explorer는 비용을 분석해 보는 도구다. 연습 계정이라도 처음에 예산 알림부터 걸어 두는 게 좋다.

비용

요금이 붙는 트래픽

다음 중 보통 요금이 붙지 않는 트래픽은?

  • 인터넷에서 S3로 올리는 트래픽
  • S3에서 인터넷으로 내려주는 트래픽
  • EC2에서 인터넷으로 나가는 트래픽
  • NAT 게이트웨이가 처리하는 트래픽

인터넷에서 AWS로 들어오는 트래픽은 보통 무료이고, AWS에서 인터넷으로 나가는 트래픽에 요금이 붙는다. NAT 게이트웨이는 켜 둔 시간과 처리한 데이터 양에 요금이 붙어서, 프라이빗 서버가 S3와 대량으로 주고받으면 S3 게이트웨이 엔드포인트로 돌리는 것만으로 비용이 크게 준다.

가용성

AZ 하나가 멈춰도

가용 영역(AZ) 하나에 장애가 나도 웹 서비스를 유지하려면?

  • 여러 AZ에 인스턴스를 두고 로드 밸런서로 나눈다
  • 한 AZ에 더 큰 인스턴스 하나를 둔다
  • 매일 EBS 스냅샷을 찍어 둔다
  • 다른 리전에 백업 파일만 둔다

AZ는 전원·네트워크가 분리된 데이터 센터 묶음이라 동시에 멈추는 일이 드물다. 서버를 여러 AZ에 나눠 두고 ALB와 오토 스케일링으로 묶으면 한 AZ가 멈춰도 나머지가 받는다. 스냅샷·백업은 복구 수단이지 멈추지 않게 해 주는 수단이 아니다.

재해 복구

RPO와 RTO

"RPO 1시간"의 뜻은?

  • 최대 1시간 치 데이터까지는 잃어도 된다
  • 1시간 안에 서비스를 되살려야 한다
  • 백업을 1시간 동안 보관한다
  • 복제가 1시간 넘게 밀리면 경보를 낸다

RPO(복구 시점 목표): 얼마만큼의 데이터를 잃어도 되나 → 백업·복제 주기를 정한다. RTO(복구 시간 목표): 얼마 만에 서비스를 되살려야 하나 → 대기 환경을 얼마나 준비해 둘지 정한다. 둘 다 짧을수록 비싸다.
