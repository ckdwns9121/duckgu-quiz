Lambda 실행 자원과 요청 제어

런타임은 코드가 실행되는 언어 환경이며 실행 역할은 함수가 AWS API에 접근할 권한이다. API Gateway에서 호출을 허용하는 resource policy·authorizer와 실행 역할은 서로 다른 경계다. 지원 런타임 패치 책임과 사용자 라이브러리 업데이트를 함께 관리한다. 메모리 설정에 비례해 CPU가 늘며 임시 실행 환경의 재사용은 영속 저장 계약이 아니다.

동시 실행은 요청률 × 평균 실행 시간으로 추정한다. 초당 100건·0.2초이면 약 20이지만 burst와 실패 재시도 여유가 필요하다. Reserved concurrency 8은 해당 함수가 동시에 최대 8개 실행되게 하면서 몫을 예약한다. Provisioned concurrency 8은 8개의 초기화 환경을 준비한다. DB 보호에는 전자, 첫 요청 지연 완화에는 후자가 직접적이다. SQS event source의 maximum concurrency도 해당 소스에 상한을 줄 수 있으며 여러 소스·다른 호출 경로가 있으면 합계를 검토한다. 배치 1·함수당 외부 호출 직렬 1개인 경우에만 함수 동시성 8이 외부 동시 요청 8로 바로 대응한다. 함수 내부 병렬 호출·다른 호출자는 별도로 합산한다.

컴퓨팅 사용량 비교는 GB × 초다. 예시 1GB×0.6초=0.6GB-s, 1.5GB×0.34초=0.51, 2GB×0.2초=0.4, 4GB×0.16초=0.64다. 목표 250ms라면 마지막 둘 중 2GB가 계산 비용이 낮다. 요청 수·아키텍처 요율이 같다는 전제이며 provisioned 비용·로그·네트워크는 별도다. 측정 없이 메모리만 줄이면 CPU 감소로 비용이 늘 수 있다.

API Gateway token bucket은 초당 보충되는 rate와 순간 소진 가능한 burst 용량을 구분한다. 한도를 넘은 요청의 429는 백오프·지터로 재시도하되 전체 재시도 횟수·기한을 정한다. API key는 사용량 식별용이며 JWT/IAM/Lambda authorizer의 인증·인가를 대신하지 않는다. HTTP API는 JWT와 단순 연동에, REST API는 지원되는 요청 검증·usage plan·캐시 요구에 맞춰 비교한다. 사용자별 캐시는 권한·캐시 키를 함께 설계한다.

출처: 실행 환경, 메모리, 동시성, SQS 확장, API throttling.

Lambda 비동기 호출과 SQS 이벤트 소스

InvocationType=Event 호출은 Lambda 내부 비동기 큐에 접수하고 202를 반환한다. 함수 코드 성공을 뜻하는 응답이 아니다. 함수 오류에는 기본 두 번 추가 실행하며, throttling·시스템 오류는 기본 최대 6시간 재시도한다. event age·retry 설정과 실패 destination 또는 함수 DLQ를 두고 오래된 이벤트 폐기·중복을 다룬다. 소비자가 72시간 멈출 수 있는 업무를 기본 Lambda 내부 큐의 6시간 처리 범위에만 맡기면 부족하다. 보존 기간을 요구에 맞춘 SQS 큐를 비교한다.

SQS event source mapping은 Lambda가 고객 SQS를 polling해서 배치를 동기 호출하는 경로다. 이 경우 실패 재노출·최종 격리는 SQS visibility/redrive와 배치 응답을 설계한다. 함수의 비동기 호출 DLQ만 설정해 SQS 실패 항목이 자동 격리된다고 가정하지 않는다. source 큐와 실패 destination의 역할·권한·보존을 구분한다.

출처: 비동기 접수, 비동기 오류 처리, SQS 연동.

SQS 수신·실패·삭제 흐름

API는 SendMessage 저장 성공을 확인한 뒤 접수 응답을 보낸다. 저장 성공 전에 응답하면 이후 전송 실패로 접수한 작업이 누락될 수 있다. 보존은 최장 소비 중단과 복구 후 따라잡기 시간을 넘게 정한다. 예를 들어 72시간 중단과 복구 여유를 견디려면 보관 기간 7일을 검토한다. 생산자는 이 큐에 전송하고 소비자는 ReceiveMessage로 받는다. 큐는 받은 메시지를 visibility timeout 동안 숨긴다. 2분 변환에는 처리 시간과 여유를 포함한 가시성을 정하고 예측하기 어려운 작업은 ChangeMessageVisibility로 연장한다. 성공 뒤 receipt handle로 삭제한다. 소비자가 죽으면 숨김이 끝나 다른 소비자가 다시 처리한다. Lambda SQS 연동은 함수 제한 시간의 최소 6배에 batch window까지 고려하라는 AWS 권장을 따른다. 보존 기간을 늘리는 것은 이 처리 중 재노출을 해결하지 않는다.

Standard는 중복·순서 역전을 허용하므로 파일 버전/이벤트 ID로 멱등 처리한다. FIFO는 주문별 MessageGroupId로 그룹 안의 큐 도착 순서를 보존한다. 같은 주문의 생성 순서가 네트워크에서 바뀌었다면 version=3이 version=2보다 먼저 큐에 올 수 있으므로 업무 버전 검증·누락 대기 정책이 필요하다. 서로 다른 주문을 같은 그룹에 몰면 병렬성이 사라진다. DeduplicationId는 5분 송신 중복을 줄이지만 장기 멱등 기록이 아니다.

poison message는 동일 입력으로 계속 실패하는 항목이다. maxReceiveCount=5 같은 redrive 기준으로 DLQ에 옮기고 알람→원인 수정→한정 속도 redrive를 한다. 너무 작은 기준은 일시 장애도 격리한다. Standard DLQ의 원래 enqueue 시각에 따른 만료와 DLQ 지표의 시각 차이를 고려하고 DLQ 보존을 원본보다 길게 둔다. FIFO에서 DLQ로 일부를 빼면 업무의 엄격한 순서가 깨질 수 있다.

부분 배치 응답 예는 다음과 같다. ReportBatchItemFailures 활성화가 전제이며 success 목록을 반환하는 형식이 아니다.

{"batchItemFailures":[{"itemIdentifier":"failed-message-id"}]}

함수가 예외를 던져 배치 전체를 실패시키면 성공 항목도 다시 실행될 수 있다. FIFO 소비자는 첫 실패에서 처리를 멈추고 실패·미처리 항목을 목록에 넣어 뒤 항목이 앞 실패를 추월하지 않게 한다. 멱등 처리는 여전히 필요하다.

출처: 가시성, DLQ, 부분 배치, FIFO.

이벤트 재분배와 선택한 규칙의 replay

이메일·재고가 같은 이벤트를 모두 받아야 하면 SNS 주제→이메일 SQS, 재고 SQS로 분배하고 각 큐 보존을 최대 장애 기간보다 길게 둔다. 한 큐에 소비자 둘을 붙이는 경쟁 소비는 각 서비스에 한 사본씩 주는 구조가 아니다. EventBridge는 AWS·SaaS·자체 이벤트를 버스에 모아 detail.country와 detail.paymentStatus 같은 필드 패턴으로 대상을 고른다. target 오류에는 재시도 정책과 DLQ를 갖춘다.

어제 회계 오류만 복구하는 예에서는 같은 버스에 결제 완료 패턴의 recovery-accounting 규칙을 만들고 활성화한다. replay에서 어제 이벤트의 time 값 범위와 이 규칙만 destination filter로 지정한다. 배송·기존 회계 규칙은 실시간 이벤트를 계속 처리한다. 모든 규칙으로 replay하면 배송도 다시 실행될 수 있다. archive가 없던 과거 이벤트는 나중에 archive를 켜도 생기지 않는다. 아카이브 저장 지연을 고려하고 replay-name 필드로 재생 이벤트를 식별할 수 있다. 재생 순서를 보장하지 않으므로 소비자는 이벤트 ID·업무 버전으로 검증한다.

SNS FIFO도 지원되는 archive/replay 기능이 있으므로 SNS 전체에 replay가 없다고 외우지 않는다. 다만 AWS 기본 이벤트·SaaS 소스 연결과 필드별 중앙 라우팅을 함께 요구하면 EventBridge가 별도 연결·분류 코드를 줄인다. SNS는 단순 fan-out과 다양한 구독 대상에, EventBridge는 이벤트 내용 기반 라우팅·AWS/SaaS 연결·archive/replay에 강점이 있다. EventBridge archive가 소비자별 SQS backlog와 같지는 않다. 복구 replay는 운영자가 범위를 선택해 새 전달을 시작하는 행위다.

출처: SNS SQS 구독, EventBridge patterns, 선택 replay, SNS FIFO archive/replay.

워크플로·callback·보상

상태 머신은 실행 단계와 전이를 정의한다. Standard는 내구 상태·최대 1년·상태 전환 과금이며 긴 승인 대기와 callback을 지원한다. Express는 최대 5분·실행/시간/메모리 과금으로 짧고 단계가 많은 작업에 적합하다. Async Express의 StartExecution은 접수만 반환하고 최소 한 번 실행될 수 있다. Sync Express의 StartSyncExecution은 완료를 기다리며 최대 한 번 실행된다. Express의 상세 실행 이력은 CloudWatch Logs 로깅을 설정해 보관하며 Standard 기본 실행 이력과 다르다. 둘 다 workflow 이름만으로 업무 멱등성이 생기지 않고 Express에는 .sync job·.waitForTaskToken이 없다.

좌석 확보→결제 요청→20분 콜백 대기→확정 흐름이면 Standard task token을 결제 연동자에게 전달하고 승인 API가 SendTaskSuccess로 이어간다. 토큰은 승인된 실행만 재개하도록 보호하고 임의 로그·브라우저 URL에 노출하지 않는다. timeout은 무한 대기를 막는다. 일시 오류는 Retry의 IntervalSeconds·BackoffRate·MaxAttempts로 제한하고 소진 후 Catch로 좌석 반환 단계로 간다. 반환은 별도 업무 API이므로 중복·실패 시 운영 조사 경로를 둔다.

반대로 2초·50단계 이벤트 정규화가 초당 1,000번이고 모두 이벤트 ID로 멱등하며 callback이 없다면 Async Express를 비교한다. 기존 상태 정의를 재사용하므로 임의 Lambda wrapper가 상태·재시도·분기 장부를 다시 구현할 필요가 줄어든다. 하지만 아주 단순한 한 작업까지 상태 머신으로 감싸는 비용이 유리하다고 단정하지 않는다.

출처: 유형 비교, 오류 처리, 서비스 연동.

Outbox·Inbox와 외부 결제의 경계

Outbox는 주문 변경과 발송 이벤트를 같은 DB 트랜잭션에 저장해 “DB는 성공, 전송은 누락”을 막는다. publisher는 outbox를 읽어 큐에 보내고 성공 표시한다. 큐 전송 후 성공 표시 전 죽으면 다시 보내므로 중복은 남는다. consumer inbox는 event_id unique 제약으로 처리 이력을 남기고 동일 DB 내부 업무 효과와 그 기록을 하나의 트랜잭션으로 확정한다.

BEGIN;
WITH accepted AS (
  INSERT INTO consumer_inbox(event_id) VALUES ('evt-103')
  ON CONFLICT (event_id) DO NOTHING
  RETURNING event_id
)
UPDATE stock SET reserved = reserved + 1
WHERE sku = 'demo-sku' AND EXISTS (SELECT 1 FROM accepted);
COMMIT;

위 PostgreSQL 예는 event_id UNIQUE/PRIMARY KEY를 전제로 INSERT가 새 행을 만든 경우만 UPDATE한다. 실제 소비자는 SKU 존재·재고 조건·영향 행 수도 검증하고 업무 변경이 실패하면 전체 rollback해 inbox 기록만 남지 않게 한다. 이력만 먼저 commit하고 업무 변경을 뒤에 하면 실패 후 영구 누락된다. 반대로 업무 변경만 먼저 commit하면 재실행으로 두 번 반영된다. 이벤트 payload의 스키마·주문 ID·버전도 검증하고 보관 기간을 재전달 기간보다 길게 정한다.

완료 상태는 영속 저장하고 재전달 시 먼저 조회해 이미 완료된 작업은 외부 API를 호출하지 않고 메시지를 확인·삭제한다. 미완료이면 외부 결과 조회와 멱등성 키로 안전하게 재개한다. 외부 결제 API 호출은 이 DB 트랜잭션에 원자적으로 묶이지 않는다. 결제 성공 뒤 응답 유실 시 event_id/주문 ID 기반의 같은 멱등성 키를 외부 API에 재사용하고 결과 조회·대사로 회복한다. 공급자가 키 결과를 7일 보관하고 재발행이 3일이면 그 범위 안에서 보호된다. 7일 뒤 재처리는 별도 차단/조회 정책이 필요하다. 큐 FIFO·Lambda 동시성·DB inbox만으로 외부 결제 exactly-once를 주장하지 않는다.

출처: 트랜잭셔널 아웃박스, 멱등 API 설계.

레거시 브로커와 SaaS 데이터 이동

Amazon MQ는 ActiveMQ/RabbitMQ 프로토콜과 브로커 의존 앱을 관리형으로 옮길 때 기능·플러그인·프로토콜 호환성을 검토하는 선택이다. SQS로 옮기면 브로커 API·라우팅 의미를 바꿔야 할 수 있다. ActiveMQ active/standby는 여러 AZ에 두 브로커를 두고 공유 영속 저장으로 장애 전환하며 서로 다른 AZ의 두 프로토콜 엔드포인트를 클라이언트 failover transport에 모두 등록하고 재연결·재시도한다. 한 엔드포인트 주소만 고정하면 대기 브로커 전환 뒤 재접속을 놓칠 수 있다. 공유 저장은 다중 AZ Amazon EFS 기반이며 persistent 메시지와 클라이언트 승인 의미를 유지한다. RabbitMQ는 다른 클러스터 배치 모델을 사용하므로 ActiveMQ의 저장·대기 모델을 그대로 적용하지 않는다. 영속 메시지 설정·승인·재연결이 없는 클라이언트에 무손실을 자동 보장하지 않는다.

AppFlow는 지원 SaaS와 AWS 간 관리형 데이터 전송이다. 정기 증분 흐름은 생성/수정 timestamp 같은 지원 필드로 이전 전송 이후 변경을 골라 full load를 줄인다. 예를 들어 Salesforce CreatedDate만 선택하면 기존 거래 금액 수정을 놓치므로 LastModifiedDate 기준 증분 전송을 선택한다. 허용 필드 mapping에서 SSN을 제외해 목적지에 전달되지 않게 한다. 소스 커넥터의 지원 필드·삭제 반영·시간대·늦은 갱신을 검증하고 재실행 중복은 대상 키로 다룬다. 임의 메시지 브로커나 업무 트랜잭션 조정기가 아니다.

출처: MQ ActiveMQ 배포, RabbitMQ 클러스터, AppFlow 예약 전송.
