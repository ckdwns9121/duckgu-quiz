지표·로그·trace·구성 이력

지표는 시간에 따른 수치, 로그는 개별 사건 내용, trace는 한 요청의 계측된 서비스 경로다. 주문 1,000개 중 998개가 2초 안에 성공하면 이 기간의 성공 SLI는 99.8%다. SLO를 99.9%로 정했다면 사용자 영향은 CPU가 낮아도 존재한다. CloudWatch 알람은 평가 기간·누락 데이터 처리·임계값·대응 대상을 정해야 한다. 평균 200ms여도 일부 사용자가 10초라면 percentile과 오류율을 함께 본다. 앱의 business metric은 앱에서 수집하고 EC2 메모리·디스크는 agent 같은 별도 수집을 구성한다.

X-Ray의 trace ID로 API→Lambda→DB 구간을 연결하면 특정 3초 요청 중 DB 대기가 2.5초였는지 볼 수 있다. 지원 통합과 앱 계측·context 전파·샘플링이 필요하며 모든 요청의 전수 감사가 아니다. 로그에 trace ID·주문 ID를 연결하되 secret과 전체 개인정보는 기록하지 않는다. Prometheus는 호환 지표·PromQL 저장/조회, Grafana는 여러 데이터 소스 시각화이며 소스 수집 자체를 자동 보장하지 않는다.

CloudTrail 관리 이벤트는 보안 그룹 AuthorizeSecurityGroupIngress의 주체·시간·요청 조건을 찾는다. S3 GetObject 같은 데이터 이벤트는 선택한 리소스 범위에 별도 활성화가 필요하다. Config는 변경 전후 IP 범위·규칙 등 지원 구성과 관계를 기록하고 규칙으로 준수 여부를 평가한다. Config 비준수 판정이 요청을 선제 차단하는 것은 아니다. 조직 trail의 리전·계정 범위와 중앙 로그 버킷의 접근·KMS·보존·Object Lock을 함께 설계한다.

IAM Access Analyzer는 CloudTrail의 관측 사용에 기초해 정책 초안을 생성할 수 있다. 지난달 호출이 없던 DR API·월말 정산을 곧바로 제거하지 않는다. 역할별 업무·예외 작업과 대조하고 시험 계정에서 최소 권한을 검증한다. 기록에 없다는 것은 미사용 증명보다 수집 범위·관측 기간 부족일 수 있다.

출처: CloudWatch SLO, X-Ray, CloudTrail 데이터 이벤트, Config, 정책 생성.

SCP 리전 예외의 논리

Organizations 루트→OU→계정의 SCP는 멤버 권한 상한이다. 명시적 Deny 하나라도 요청에 맞으면 하위 Allow로 지울 수 없다. Allow-list 전략에서는 각 계층에서 Allow가 이어져야 하며 어느 수준의 필요한 Allow 누락도 제한이다. SCP는 관리 계정의 주체와 서비스 연결 역할 등에 적용되지 않는 예외가 있으므로 관리 계정에 업무를 몰아 제한하려 하지 않는다.

다음은 EC2만을 대상으로 서울 기본 허용, 운영 계정 111122223333의 정확한 DRDeploy 역할만 시드니 추가 허용하는 Deny 조각이다. 기존 FullAWSAccess 등 상한 Allow와 해당 역할 IAM 허용은 별도 전제다. 다른 상위 Deny가 있으면 이 조각만으로 예외가 생기지 않는다.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyEC2OutsideSeoulAndSydney",
      "Effect": "Deny",
      "Action": "ec2:*",
      "Resource": "*",
      "Condition": {
        "StringNotEquals": {
          "aws:RequestedRegion": ["ap-northeast-2", "ap-southeast-2"]
        }
      }
    },
    {
      "Sid": "DenySydneyExceptExactDRRole",
      "Effect": "Deny",
      "Action": "ec2:*",
      "Resource": "*",
      "Condition": {
        "StringEquals": {"aws:RequestedRegion": "ap-southeast-2"},
        "ArnNotEquals": {
          "aws:PrincipalArn": "arn:aws:iam::111122223333:role/DRDeploy"
        }
      }
    }
  ]
}
요청 첫 Deny 둘째 Deny SCP 결과
어느 역할·서울 불일치 불일치 이 두 문장에서 거부하지 않음
정확한 DRDeploy·시드니 불일치 ARN 예외로 불일치 이 두 문장에서 거부하지 않음
다른 역할·시드니 불일치 일치 거부
정확한 DRDeploy·다른 리전 일치 불일치 거부

각 문장의 서로 다른 조건은 AND, 여러 Deny 문장 중 하나라도 맞으면 거부다. StringNotEquals의 여러 지역 값은 어느 값에도 같지 않을 때 참이 된다. 역할만 조건에서 빼면 그 역할이 모든 금지 리전으로 갈 수 있는 잘못된 예외가 된다. AssumeRole 세션에서도 aws:PrincipalArn은 해당 역할 ARN으로 평가한다. 모든 AWS API의 리전을 제한하려면 IAM·Route 53 같은 글로벌 서비스, 교차 리전 효과와 지원 조건 키를 따로 검토해야 한다. 이 예를 무작정 Action:*로 확장하지 않는다.

Permissions boundary는 IAM 역할/사용자에 대한 상한이고 SCP는 조직 멤버 계정 상한이다. 둘 다 권한을 주지 않는다. 계정 관리자가 boundary를 수정·제거할 수 있다면 관리자 우회 방지 요구에는 조직 SCP가 맞다. ABAC에서는 PrincipalTag/Project와 ResourceTag/Project 비교 외에 Create/Tag/Untag·세션 태그 허용을 제한한다. 사용자가 자기 태그를 Project=B로 바꿀 수 있으면 Project=A 제한이 무너진다.

출처: SCP 평가, 조건 논리, PrincipalArn, Boundary, ABAC.

직원 배정과 기존 계정 등록

Identity Center는 외부 IdP에서 동기화한 그룹의 permission set을 계정에 배정한다. 예를 들어 분석팀은 개발 계정 ReadOnly와 운영 계정 제한 조회 권한을 각각 받고 임시 세션으로 접근한다. permission set은 정책·세션 설정의 템플릿이며 SCP 거부를 넘지 않는다. 계정별 IAM 사용자와 비밀번호를 복제하는 운영을 줄이되 퇴사 처리·동기화·세션 만료를 함께 관리한다.

Control Tower는 Organizations 계정과 OU 위에 landing zone의 baseline·로그·지원 통제를 배포하고 수명 주기를 관리한다. 기존 계정은 같은 조직 내 적격 계정인지, 등록 OU와 홈/관리 리전 조건을 충족하는지, AWSControlTowerExecution 역할과 권한이 있는지 확인한다. 기존 Config recorder/delivery channel·trail은 충돌과 중복 비용을 검토하며 문서의 지원 이관 절차를 따른다. 설명을 위해 기존 감사 기록을 무조건 지우는 방식은 피한다.

자동 계정 등록이 꺼져 있는 예에서는 계정을 등록된 OU에 이동시킨 것만으로 완료하지 않는다. Control Tower의 Enroll account 또는 지원 API/계정 등록 절차를 실행해 baseline·통제 적용 상태와 오류를 확인한다. 기존 VPC와 앱은 그대로이므로 네트워크 구조를 새로 만들어주리라 기대하지 않는다. IAM Identity Center 배정·SCP 적용·Control Tower 등록은 서로 연결되지만 다른 결과를 만든다.

출처: 권한 세트, 기존 계정 등록, 등록 전제 조건.

리소스 교체·삭제·rollback

Change set의 Replacement는 새 physical ID를 생성한다는 신호이며 업무 데이터 이관까지 자동 수행한다는 뜻이 아니다. 이전 DB를 검증 동안 실행 상태로 보관하고 스택을 나중에 지울 때 현재 DB는 최종 snapshot 후 삭제하려면 다음 두 속성을 함께 둔다.

OrdersDB:
  Type: AWS::RDS::DBInstance
  DeletionPolicy: Snapshot
  UpdateReplacePolicy: Retain
  Properties:
    # 실제 배포에는 엔진·크기·네트워크·자격 증명 등 필수 속성이 필요하다.
    Engine: mysql

UpdateReplacePolicy Retain은 교체되어 빠지는 이전 DB를 남겨 스택 관리에서 제외한다. Snapshot이면 snapshot 후 이전 DB를 삭제하므로 “실행 가능한 이전 DB”와 다르다. DeletionPolicy Snapshot은 나중에 스택 삭제나 리소스 정의 제거 시 현재 DB를 snapshot 후 삭제한다. 일반 기본 삭제와 일부 RDS 리소스 기본 Snapshot 예외를 구분한다. Snapshot은 EBS/RDS/일부 캐시·웨어하우스 등 지원 유형만 가능하며 S3처럼 미지원 유형의 UpdateReplacePolicy Snapshot은 Delete로 돌아갈 수 있으므로 지원 목록을 확인한다. Retain 리소스·snapshot은 비용과 보안·수동 정리 책임이 남는다.

Drift detection은 지원 리소스의 명시한 속성을 실제 상태와 비교한다. 지원하지 않는 속성·앱 데이터까지 모두 검사하지 않는다. 수동 긴급 변경 후 템플릿 반영 여부를 결정한다. Update rollback은 이전 인프라 상태 복귀를 시도하지만 실패할 수도 있고 외부 API·데이터 삭제를 되돌리지 않는다. RDS 복구·재연결·데이터 검증을 별도 준비한다.

출처: DeletionPolicy, UpdateReplacePolicy, drift, rollback 복구.

구·신 앱 공존과 expand-contract

customer_name을 display_name으로 바꾸는 예에서 첫 배포는 새 nullable 컬럼을 추가한다(expand). 기존 행을 backfill하고 진행률·누락·불일치를 검증한다. 구 앱이 여전히 customer_name을 읽는 동안 신 앱은 두 필드 호환 읽기와 필요한 dual-write를 수행한다. dual-write의 원자성·실패 복구를 같은 DB 트랜잭션이나 변경 이벤트 대사로 보장한다. 한쪽만 성공한 쓰기를 방치하면 데이터가 갈라진다.

신 앱 전체 전환과 rollback 기간이 끝난 뒤 구 앱·배치·리포트 의존이 없는지 확인하고 구 컬럼을 제거한다(contract). 첫 배포에서 바로 rename/drop하면 구 앱의 쿼리가 깨진다. 새 DB로 물리 교체한다면 backfill뿐 아니라 마지막 변경 복제·쓰기 전환·차이 검사·되돌릴 쓰기 처리도 필요하다. CloudFormation Retain은 원본을 남길 뿐 동기화나 앱 호환성을 만들지 않는다.

출처: CloudFormation 업데이트 방식, 안전한 배포와 rollback.

Systems Manager 운영의 전제 조건

Session Manager는 인바운드 SSH 없이 승인 사용자 세션을 연결하지만 노드가 서비스로 아웃바운드 통신할 수 있어야 한다. 지원 OS·SSM Agent 실행·인스턴스 역할의 Systems Manager 권한·사용자의 StartSession 대상/문서 권한·엔드포인트 443 경로를 확인한다. 인터넷이 없으면 필요한 ssm/ssmmessages 등 해당 리전·agent 버전의 interface endpoint와 private DNS·SG를 구성하고 로그용 S3/CloudWatch/KMS 경로도 준비한다. 사용자 IAM Allow만 있어도 agent가 offline이면 접속할 수 없다.

세션 로그는 설정해야 하며 SSH 또는 port forwarding 터널의 세션 내용 로깅에는 제한이 있다. “모든 작업 내역 필수”라면 일반 Session Manager shell 기록과 CloudTrail 시작/종료 기록, 허용 문서·세션 유형을 명시한다. Run Command 문서·대상 태그를 좁히고 과도한 명령 권한을 피한다.

Patch Manager는 패치 baseline·승인 규칙·대상·maintenance window·동시성·실패 기준을 정한다. 다운로드 repository 네트워크, 재부팅 여부, 앱 smoke check와 되돌리기 계획이 필요하다. 패치 적용 성공이 업무 정상이나 모든 취약점 제거를 뜻하지 않는다. Fleet Manager는 노드 운영 화면, Automation은 반복 운영 단계를 묶는 runbook이다.

출처: Session 전제, 사설 연결, session logging, Patch Manager.

비용 원장·상각·컨테이너 배분

Cost Explorer는 계정/서비스/활성 비용 할당 태그로 월별 원인을 좁힌다. 선결제 Savings Plans 구매월의 현금 청구 대신 사용 기간에 나눈 비용을 보려면 amortized cost 관점을 선택한다. Budgets에는 같은 태그 필터·비용 관점과 실제 누적/월말 예상 초과 알림을 정해 이메일을 연결한다. 알림·지원 budget action은 데이터 반영 지연과 이미 실행 중인 리소스 때문에 실시간 hard cap이 아니다.

CUR와 Data Exports는 상세 사용량·요율·할인·계정·태그 등 원장을 S3에 내보내 Athena 등으로 계산한다. 팀 A 컨테이너가 공유 EC2의 일부 CPU/메모리를 썼다면 인스턴스 태그 하나만으로 컨테이너별 비용을 정확히 나눌 수 없다. 지원 ECS/EKS에 split cost allocation data를 활성화하고 비용 할당 태그·Kubernetes label 지원과 활성화를 구성해 작업/pod별 자원 사용 기반 배분 데이터를 받는다. ECS task와 EKS pod의 지원 필드·수집 방식이 다르므로 해당 런타임을 확인한다. 미할당·유휴·공유 네트워크 비용의 배분 규칙도 공개해 팀 합계와 청구 합계가 맞는지 대사한다. CloudWatch CPU만 수작업 비율로 나누면 할인·유휴·메모리 비용을 빠뜨릴 수 있다.

Compute Optimizer는 실제 관측 지표로 크기 조정 후보를 준다. 월말 spike·성장·SLO·메모리 수집 상태와 함께 검증하고 자동 절감 보장으로 보지 않는다. 비용 태그는 권한 통제·업무 팀의 실제 소유권을 자동 증명하지 않는다.

출처: Cost Explorer 상각, Budgets, Data Exports, Split 비용, Compute Optimizer.

공유 NAT·TGW 비용의 대사

중앙 네트워크 계정의 CUR/Data Exports를 Athena로 조회해 NAT/TGW 처리 요금과 시간 요금을 계정·리소스·사용 유형별로 분리한다. 공용 NAT의 NetworkTeam 태그는 소유 팀만 알려주며 이를 통과한 여러 소비 팀을 구별하지 못한다. VPC/TGW Flow Logs의 원본 ENI/VPC를 팀 대응표에 연결하고 같은 경로의 양방향·여러 관측 지점 바이트 중복을 제거한 배분 근거를 만든다. 로그 바이트와 청구 처리량은 집계 범위·지원/누락 트래픽·로그 누락·단위가 달라 항상 같지 않다.

예를 들어 실제 처리 요금 100에 신뢰할 수 있는 측정 비중 A 60%, B 30%, 미귀속 10%이면 각각 60·30·10으로 공개한다. 측정 합계와 청구 기준의 잔여 차이는 별도 reconciliation 항목으로 남기고 원인을 조사한다. 시간 요금 40은 미리 합의한 고정 규칙으로 따로 배분한다. EC2 비용 비중이나 팀 수로 균등 나누면 요청한 트래픽 비례 처리 요금과 다르다. 월별 팀 합계+미귀속+조정이 실제 청구와 맞는지 대사한다.

출처: CUR Athena 조회, Flow Logs 레코드, TGW Flow Logs.

복구 리전의 할당량과 재시도 폭증

DR에서 데이터와 템플릿이 있어도 대상 리전 EC2 vCPU·Lambda 동시성·API 시작률·EIP·DB 등 한도가 부족하면 RTO를 지키지 못한다. Service Quotas에서 계정·리전별 한도를 확인하고 조정 가능 항목은 사전에 요청한다. quota 요청 승인·리소스 실제 capacity를 같은 것으로 보지 않는다. 리허설에서 복원/생성 API throttling과 큐 backlog 처리율까지 측정한다.

복구 직후 backlog를 최대 속도로 풀면 DB·외부 API가 다시 실패한다. 제한 동시성·큐 소비 rate·지수 백오프·지터·최대 재시도/기한을 두고 원본 작업의 멱등성으로 중복 부작용을 막는다. 지속 병목을 무한 재시도로 숨기지 않고 queue age·DLQ·오류율·SLO를 경보한다. AWS Health는 계정 관련 AWS 사건·예정 변경을 알려주지만 앱 오류 원인 분석과 다르다.
