PART 1

Docker 이미지 · 빌드

빌드 캐시가 매번 깨지고, 비밀 값이 레이어에 남고, 실행 이미지가 불필요하게 커지는 원인을 Dockerfile에서 찾습니다.

빌드 캐시

소스 한 줄에 의존성을 다시 받을 때

Node 앱에서 소스 한 줄만 바꿔도 npm ci가 매번 다시 실행된다. 캐시를 가장 잘 재사용하는 Dockerfile 순서는?

  • lockfile 복사 → npm ci → 소스 복사
  • 소스 전체 복사 → npm ci → lockfile 복사
  • npm ci → 소스 복사 → lockfile 복사
  • 소스 전체 복사 → npm ci → 소스 전체 재복사
  • 앞 레이어부터 달라져 npm ci도 다시 실행된다
  • package.json이 같으면 항상 재사용된다
  • RUN 명령은 파일 변경과 무관하게 재사용된다
  • 마지막 CMD만 다시 만들어지고 나머지는 유지된다

Docker는 앞 레이어가 달라지면 그 뒤 레이어도 다시 만든다. 자주 안 바뀌는 package.json과 lockfile을 먼저 복사해 의존성을 설치하고, 자주 바뀌는 소스는 나중에 복사해야 코드 수정 때 설치 캐시를 살릴 수 있다.

캐시 무효화

최신 패키지를 기대했는데 그대로일 때

Dockerfile의 RUN apt-get update 명령 문자열이 같고 앞 레이어도 같다. 일주일 뒤 다시 빌드하면?

  • 캐시를 재사용해 update가 실행되지 않을 수 있다
  • 저장소 날짜를 비교해 반드시 다시 실행한다
  • apt 명령은 매 빌드마다 캐시를 무시한다
  • 이미지 태그가 같으면 전체 빌드가 실패한다
  • docker build --pull --no-cache
  • docker build --force-recreate
  • docker build --refresh-layers
  • docker pull 뒤 docker start

일반 RUN 캐시는 컨테이너 안 파일의 최신 상태를 검사하지 않고 명령과 이전 레이어를 본다. --no-cache는 빌드 단계를 다시 실행하지만 베이스 이미지를 새로 받는 옵션은 아니므로, 둘 다 원하면 --pull을 함께 쓴다.

멀티 스테이지

컴파일러가 운영 이미지에 남을 때

Go 앱 운영 이미지에 컴파일러와 소스가 모두 들어가 이미지가 크다. 가장 적절한 개선은?

  • 빌드 단계의 바이너리만 최종 단계로 복사한다
  • 한 단계에서 빌드 후 소스를 rm으로 지운다
  • 컨테이너 시작 시마다 바이너리를 컴파일한다
  • 운영 이미지를 압축 파일로 감싸서 실행한다
  • 마지막 단계와 COPY --from으로 가져온 파일
  • 모든 단계의 파일 시스템 전체
  • 이름이 build인 단계의 모든 레이어
  • 첫 단계에 설치한 패키지와 캐시 전체

멀티 스테이지 빌드는 컴파일·테스트 도구가 있는 단계와 실행 단계를 분리한다. 마지막 단계에는 그 단계의 베이스와 COPY --from으로 고른 산출물만 남아 이미지 크기와 공격 표면이 줄어든다. 같은 단계에서 삭제하면 이전 레이어에는 파일이 남을 수 있다.

빌드 보안

레지스트리 토큰이 이미지에 남을 때

비공개 패키지를 받으려고 토큰을 ARG로 전달해 RUN에서 사용했다. 왜 위험할까?

  • 이미지 메타데이터나 빌드 기록에 남을 수 있다
  • ARG는 컨테이너 포트를 자동으로 공개한다
  • ARG를 쓰면 멀티 스테이지 빌드가 꺼진다
  • 토큰이 컨테이너의 PID 1로 실행된다
  • RUN --mount=type=secret을 사용한다
  • ENV TOKEN을 최종 단계에 선언한다
  • 토큰 파일을 COPY한 뒤 다음 RUN에서 지운다
  • LABEL에 토큰을 넣고 빌드 뒤 덮어쓴다

빌드 인수와 환경 변수는 비밀 전달 수단이 아니다. 파일을 복사한 뒤 다음 레이어에서 지워도 앞 레이어에서 복구할 수 있다. BuildKit의 secret 마운트는 해당 RUN 동안만 비밀을 노출하고 결과 레이어에 포함하지 않는다.

빌드 컨텍스트

빌드 전송이 느리고 키 파일도 보일 때

docker build . 시작 단계에서 수 GB가 전송되고 node_modules와 .git도 포함된다. 가장 먼저 할 일은?

  • .dockerignore에서 불필요한 경로를 제외한다
  • Dockerfile의 EXPOSE 줄을 삭제한다
  • 컨테이너에 tmpfs를 마운트한다
  • 이미지 태그를 latest에서 stable로 바꾼다
  • secrets/는 빌드 컨텍스트와 COPY 대상에서 빠진다
  • COPY가 ignore보다 우선해 이미지에 들어간다
  • 파일은 복사되지만 docker history에서만 숨겨진다
  • 최종 이미지에서는 빠지지만 빌드 단계에는 들어간다

.dockerignore는 빌더에 보낼 컨텍스트 자체에서 파일을 제외한다. 전송량과 캐시 무효화를 줄이고 키·로컬 의존성의 우발적 복사를 막는다. 다만 이미 Git에 올라간 비밀이나 외부에서 내려받는 비밀까지 보호하는 기능은 아니다.

재현 가능한 빌드

같은 태그인데 결과가 달라질 때

node:22 태그가 가리키는 이미지 변경까지 막아 완전히 같은 베이스를 쓰려면?

  • 이미지 다이제스트로 고정한다
  • 컨테이너 이름을 node-22로 고정한다
  • EXPOSE에 Node 버전을 적는다
  • 빌드할 때 --no-cache만 사용한다
  • 다이제스트 갱신을 자동 PR로 받아 검토한다
  • latest 태그를 영구히 로컬 캐시에서만 쓴다
  • 실행 중인 컨테이너 안에서 apt upgrade한다
  • 매 시작마다 Dockerfile을 다시 생성한다

태그는 다른 이미지로 이동할 수 있지만 다이제스트는 특정 콘텐츠를 가리킨다. 다이제스트 고정은 재현성을 주는 대신 보안 수정도 자동으로 들어오지 않으므로, 의존성 업데이트 도구가 새 다이제스트를 제안하고 CI와 검토를 거쳐 갱신하게 만드는 방식이 실용적이다.

PART 2

Docker 런타임 · Compose

컨테이너가 사라질 때 데이터가 없어지고, localhost 연결이 실패하고, 종료 신호가 앱까지 닿지 않는 이유를 런타임 관점에서 다룹니다.

데이터 영속성

컨테이너를 다시 만들자 DB가 비었을 때

PostgreSQL 데이터를 컨테이너의 쓰기 레이어에만 저장했다. 컨테이너를 삭제하고 새로 만들면?

  • 기존 데이터는 사라진다
  • 같은 이미지면 데이터가 자동 복구된다
  • 컨테이너 이름이 같으면 데이터가 연결된다
  • Docker가 삭제 전에 자동 스냅샷을 만든다
  • 이름 있는 볼륨을 데이터 경로에 마운트한다
  • 이미지의 VOLUME 줄만 지운다
  • 컨테이너의 restart 정책을 always로 둔다
  • 매 요청마다 docker commit을 실행한다

컨테이너의 쓰기 레이어는 컨테이너와 수명을 같이한다. 볼륨은 컨테이너 밖에서 Docker가 관리하므로 컨테이너를 삭제해도 남고, 쓰기 많은 DB에도 쓰기 레이어보다 적합하다. 볼륨 자체를 삭제하면 데이터도 없어지므로 백업은 별도로 필요하다.

마운트

이미지 안 파일이 갑자기 안 보일 때

이미지의 /app에 빌드 결과가 있지만 빈 호스트 폴더를 /app에 bind mount하자 파일이 안 보인다. 이유는?

  • 마운트가 이미지의 기존 /app 내용을 가렸다
  • bind mount가 이미지 레이어를 영구 삭제했다
  • Docker가 빈 폴더를 이미지에 다시 빌드했다
  • 컨테이너의 WORKDIR가 자동으로 루트로 바뀌었다
  • bind mount를 readonly로 설정한다
  • 파일을 EXPOSE 목록에 넣는다
  • 컨테이너 이름에 read-only를 붙인다
  • 호스트 경로 대신 컨테이너 ID를 마운트한다

마운트 대상 경로에 이미지 파일이 있어도 마운트가 그 내용을 가린다. 컨테이너를 마운트 없이 다시 만들면 원래 파일이 보인다. bind mount는 기본이 쓰기 가능해 호스트 파일도 바꿀 수 있으므로 필요하지 않다면 readonly로 제한한다.

포트

EXPOSE했는데 접속이 안 될 때

Dockerfile에 EXPOSE 3000만 적고 컨테이너를 실행했다. 호스트의 localhost:3000으로 접속하면?

  • 포트 게시를 안 했으므로 연결되지 않는다
  • EXPOSE가 자동으로 같은 호스트 포트를 연다
  • HTTP만 자동 게시되고 TCP는 게시되지 않는다
  • root 사용자로 실행했을 때만 연결된다
  • -p 8080:3000
  • -p 3000:8080
  • --expose 8080:3000
  • --network 8080=3000

EXPOSE는 이미지가 어느 포트를 쓰는지 설명하는 메타데이터이며 호스트 방화벽이나 포트 매핑을 만들지 않는다. -p 호스트:컨테이너로 게시해야 호스트에서 접근할 수 있다.

컨테이너 네트워크

웹 컨테이너가 DB에 못 붙을 때

Compose의 web 컨테이너가 localhost:5432로 db 컨테이너에 연결하려 한다. 왜 실패할까?

  • localhost는 web 컨테이너 자신을 가리킨다
  • Compose 네트워크는 HTTP만 허용한다
  • PostgreSQL은 컨테이너 사이 통신을 막는다
  • 서비스 이름은 포트 번호로만 해석된다
  • Compose 서비스 이름 db
  • 호스트의 localhost
  • 실행 때마다 바뀌는 컨테이너 IP를 직접 입력
  • 이미지 이름 postgres

각 컨테이너는 자기 네트워크 네임스페이스를 가져 localhost가 자기 자신이다. Compose 기본 네트워크에서는 서비스 이름이 DNS 이름이 되므로 db:5432처럼 연결한다. 컨테이너 IP는 재생성 때 바뀔 수 있어 직접 고정하지 않는다.

프로세스 종료

종료 때 요청이 잘릴 때

CMD ["node", "server.js"] 같은 exec 형식이 종료 신호 처리에 유리한 이유는?

  • 앱이 PID 1이 되어 신호를 직접 받는다
  • 앱이 자동으로 root 권한을 버린다
  • Docker가 앱 코드를 미리 컴파일한다
  • 모든 자식 프로세스가 별도 컨테이너가 된다
  • 종료 신호가 앱에 제대로 전달되지 않을 수 있다
  • 컨테이너 포트가 임의로 바뀐다
  • 이미지 레이어가 실행 때마다 합쳐진다
  • 볼륨이 자동으로 읽기 전용이 된다

exec 형식 CMD ["node", "server.js"]은 앱을 PID 1로 실행해 Docker의 종료 신호를 직접 받게 한다. 셸 형식은 /bin/sh -c가 PID 1이 되어 신호 전달과 좀비 프로세스 회수가 어긋날 수 있다. 앱은 SIGTERM에서 새 요청을 멈추고 진행 중 작업을 정리해야 한다.

Docker Compose

DB 컨테이너는 떴는데 앱이 실패할 때

web에 depends_on으로 db를 적었는데 시작 직후 연결 실패가 난다. 원인은?

  • 기본 의존성은 DB가 준비될 때까지 기다리지 않는다
  • depends_on은 종료 순서에만 적용된다
  • Compose는 서비스 사이 DNS를 만들지 않는다
  • DB 포트는 호스트에 게시해야만 접근된다
  • service_healthy 조건을 쓴다
  • web의 restart를 no로 설정한다
  • DB에 EXPOSE만 추가한다
  • 두 서비스를 host 네트워크로 바꾼다

컨테이너가 실행 중인 것과 애플리케이션이 준비됨은 다르다. Compose의 짧은 depends_on은 시작 순서만 보장한다. DB에 실제 준비 상태를 검사하는 healthcheck를 두고 condition: service_healthy를 사용해야 한다. 앱 자체의 재시도도 함께 두는 편이 안전하다.

PART 3

Pod · Deployment · 리소스

Pod가 반복 재시작되고 배포가 멈추며 스케줄링되지 않는 상황을 컨트롤러·프로브·리소스 설정으로 진단합니다.

워크로드

노드 장애 뒤 Pod가 돌아오지 않을 때

kubectl run으로 만든 단독 Pod가 삭제된 뒤 다시 생성되지 않는다. 이유는?

  • 원하는 복제 수를 관리하는 컨트롤러가 없어서
  • Pod 이름에 하이픈이 들어가서
  • kubelet은 종료된 Pod를 절대 확인하지 않아서
  • Service가 없는 Pod는 한 번만 실행돼서
  • Deployment
  • 단독 Pod 세 개
  • ConfigMap
  • ClusterIP Service만 생성

Pod 자체는 원하는 상태를 계속 복구하는 컨트롤러가 아니다. Deployment가 ReplicaSet을 관리해 지정한 복제 수를 유지하고 템플릿 변경을 롤링 업데이트한다. 일회성 완료 작업은 Job, 안정된 이름과 저장소가 필요한 워크로드는 StatefulSet을 검토한다.

라벨

Deployment가 Pod를 세지 못할 때

Deployment의 selector는 app=api인데 Pod 템플릿 라벨은 app=web이다. 적용 결과는?

  • selector와 템플릿 라벨 불일치로 거부된다
  • 두 종류의 Pod가 절반씩 생성된다
  • selector가 템플릿 라벨로 자동 변경된다
  • Pod는 생성되지만 Service만 연결되지 않는다
  • 새 Deployment를 만들고 트래픽을 전환한다
  • 기존 Pod의 UID를 selector로 넣는다
  • ReplicaSet을 수동으로 삭제하면 selector가 바뀐다
  • kubelet을 재시작하면 수정 가능해진다

Deployment의 selector는 자신이 관리할 Pod 집합을 정하며 Pod 템플릿 라벨과 맞아야 한다. 생성 후 selector 변경은 기존 ReplicaSet과 소유 관계를 뒤섞을 수 있어 허용되지 않는다. 다른 selector가 필요하면 새 Deployment로 이동한다.

상태 검사

살아 있지만 트래픽은 받으면 안 될 때

앱은 실행 중이지만 DB 연결이 끊겨 요청을 처리할 수 없다. 재시작보다 Service 대상에서 잠시 빼고 싶다면?

  • readiness probe가 실패하게 한다
  • liveness probe를 즉시 실패시킨다
  • startup probe를 계속 성공시킨다
  • Pod의 restartPolicy를 Never로 바꾼다
  • liveness probe
  • readiness probe
  • Service selector
  • PodDisruptionBudget

readiness 실패는 컨테이너를 살려 둔 채 Service 엔드포인트에서 제외한다. liveness 실패는 kubelet이 컨테이너를 재시작한다. 의존성의 일시 장애를 liveness로 검사하면 재시작 폭풍이 날 수 있으므로 회복 불가능한 내부 상태만 검사한다.

상태 검사

느린 시작 때문에 계속 재시작될 때

시작에 2분 걸리는 레거시 앱이 liveness 검사에 계속 실패해 준비되기 전에 재시작된다. 적절한 해결은?

  • startup probe로 초기화 시간을 보호한다
  • readiness probe를 삭제한다
  • Service를 NodePort로 바꾼다
  • liveness 성공 코드를 500으로 바꾼다
  • 두 검사 모두 시작되지 않는다
  • 둘 다 같은 주기로 계속 실행된다
  • readiness만 실행되고 liveness는 삭제된다
  • liveness 실패 횟수가 startup에 합산된다

startup probe가 있으면 성공할 때까지 liveness와 readiness를 시작하지 않는다. 느린 초기화 시간을 넉넉히 주면서도 시작이 끝난 뒤에는 더 빠른 liveness 주기로 실제 교착을 감지할 수 있다.

CPU · 메모리

Pending과 OOMKilled 구분하기

Pod의 CPU request가 어떤 노드의 남은 할당 가능 CPU보다도 크다. Pod 상태는?

  • 스케줄할 노드가 없어 Pending에 머문다
  • 가장 큰 노드에 배치된 뒤 CPU가 제한된다
  • 실행 후 즉시 OOMKilled가 된다
  • request를 무시하고 BestEffort로 실행된다
  • OOM으로 종료되고 정책에 따라 재시작된다
  • request 값까지 자동으로 메모리가 늘어난다
  • CPU만 스로틀되고 프로세스는 계속 돈다
  • 다른 노드로 실행 중인 컨테이너가 이동한다

request는 스케줄러가 자리 계산에 쓰고, limit은 실행 중 사용 상한에 관여한다. CPU 초과는 보통 스로틀되지만 메모리 limit 초과는 OOM 종료로 이어질 수 있다. 실행 중 컨테이너가 다른 노드로 이동하는 것이 아니라 새 Pod가 다시 배치된다.

롤링 배포

새 버전이 준비되지 않아 배포가 멈출 때

새 이미지의 readiness probe가 계속 실패한다. RollingUpdate Deployment는 일반적으로 어떻게 될까?

  • 새 Pod를 준비되지 않은 채 두고 교체 진행이 막힌다
  • Service가 준비 안 된 새 Pod에도 트래픽을 보낸다
  • 기존 Pod를 모두 먼저 지운 뒤 계속 진행한다
  • readiness 실패를 무시하고 배포 성공으로 기록한다
  • 4개
  • 0개
  • 1개
  • maxSurge와 같은 수

Deployment는 새 Pod가 Ready가 되는 것을 보며 기존 Pod를 줄인다. maxUnavailable: 0이면 원하는 복제 수만큼 준비 상태를 유지해야 하므로 새 Pod를 추가할 여유인 maxSurge도 필요하다. readiness가 영구 실패하면 진행 기한 초과로 진단할 수 있다.

장애 진단

재시작 직전 로그가 사라졌을 때

CrashLoopBackOff Pod의 현재 로그에는 시작 메시지만 있다. 직전 종료된 컨테이너 로그를 보려면?

  • kubectl logs --previous를 사용한다
  • kubectl get pod --watch만 실행한다
  • kubectl apply --force를 실행한다
  • Service의 EndpointSlice를 삭제한다
  • 이미지 이름·태그와 imagePullSecrets
  • readiness probe의 응답 본문
  • Service의 externalTrafficPolicy
  • PVC의 reclaimPolicy

CrashLoopBackOff는 반복 실패 사이의 대기 상태다. describe의 이벤트·종료 이유와 logs --previous를 함께 본다. ImagePullBackOff는 앱이 시작되기 전 이미지 가져오기 실패이므로 레지스트리 주소, 태그, 인증 Secret과 노드 네트워크를 확인한다.

PART 4

Service · Ingress · NetworkPolicy

Service에 엔드포인트가 없고, 포트가 엇갈리고, 기본 거부 정책 뒤 DNS까지 끊기는 네트워크 장애를 다룹니다.

Service

Service IP는 되는데 연결이 거부될 때

Service selector는 app=api인데 Pod 라벨은 app=backend다. EndpointSlice에는 무엇이 생길까?

  • 일치하는 Pod가 없어 엔드포인트가 비어 있다
  • 같은 namespace의 모든 Pod가 들어간다
  • Pod 이름에 api가 있으면 자동으로 들어간다
  • Service가 Pod 라벨을 app=api로 바꾼다
  • Service selector와 Pod 라벨
  • ConfigMap 키와 Secret 값
  • 노드 이름과 PVC 용량
  • Ingress host와 ServiceAccount

selector가 있는 Service는 일치하는 Pod를 찾아 EndpointSlice를 자동으로 만든다. Service ClusterIP가 존재해도 엔드포인트가 비어 있으면 전달할 대상이 없다. kubectl get endpointslice와 양쪽 라벨을 비교한다.

Service

포트 번호가 세 군데 다를 때

Service의 port는 80, targetPort는 8080이고 앱은 컨테이너에서 8080을 듣는다. 클러스터 내부 클라이언트는 어디로 접속할까?

  • Service 주소의 80 포트
  • Service 주소의 8080 포트만 가능하다
  • Pod IP의 80 포트로만 가능하다
  • 노드 IP의 임의 포트가 반드시 필요하다
  • containerPort에 이름 http인 포트가 있어야 한다
  • Pod 이름이 http로 시작해야 한다
  • namespace에 http라는 ConfigMap이 있어야 한다
  • Ingress class 이름을 http로 정해야 한다

port는 클라이언트가 Service에 접속하는 포트, targetPort는 백엔드 Pod로 전달할 포트다. 이름 있는 targetPort는 Pod의 이름 있는 컨테이너 포트를 찾아 서로 다른 버전의 실제 포트도 같은 Service로 연결할 수 있다.

Service 유형

노출 범위를 잘못 고를 때

클러스터 안의 다른 Pod만 접근할 내부 API에 가장 기본적인 Service 유형은?

  • ClusterIP
  • NodePort
  • LoadBalancer
  • ExternalName으로 외부 IP 직접 지정
  • LoadBalancer
  • ClusterIP와 hostNetwork
  • ExternalName과 Pod IP
  • Headless Service와 localhost

ClusterIP는 기본 내부 가상 IP다. NodePort는 각 노드의 포트를 열고, LoadBalancer는 지원되는 환경에서 외부 로드 밸런서 프로비저닝을 요청한다. HTTP 경로·호스트 라우팅이 여러 개면 Ingress나 Gateway API를 함께 검토한다.

Ingress

객체를 만들었는데 외부 주소가 없을 때

Ingress 리소스를 적용했지만 외부 주소도 라우팅도 생기지 않는다. 가장 흔한 원인은?

  • Ingress 컨트롤러가 설치되거나 선택되지 않았다
  • Ingress는 StatefulSet만 대상으로 삼아서
  • 모든 Service가 NodePort여야만 해서
  • Pod에 PVC가 없으면 주소를 만들지 않아서
  • 별도 DNS 설정이나 자동화가 필요하다
  • Kubernetes가 도메인 등록까지 자동 처리한다
  • CoreDNS가 인터넷 DNS에 자동 게시한다
  • ServiceAccount 이름으로 CNAME이 생성된다

Ingress는 원하는 HTTP 라우팅 규칙을 선언할 뿐 실제 구현은 Ingress 컨트롤러가 한다. 외부 IP나 로드 밸런서 주소에 도메인이 향하도록 DNS도 별도로 설정해야 한다. IngressClass가 여러 개면 어떤 컨트롤러가 처리할지도 명시한다.

NetworkPolicy

정책을 추가하자 DNS까지 끊길 때

namespace에 NetworkPolicy가 하나도 없다. 기본적인 Pod ingress·egress 동작은?

  • 둘 다 허용된다
  • 둘 다 기본 거부된다
  • ingress만 허용되고 egress는 거부된다
  • 같은 라벨끼리만 허용된다
  • 클러스터 DNS로 가는 DNS 트래픽
  • 모든 Pod의 hostNetwork 사용
  • API 서버의 익명 인증
  • Service의 sessionAffinity

NetworkPolicy가 선택하지 않은 Pod의 트래픽은 기본 허용이다. 허용 목록 방식은 모든 Pod를 선택하는 기본 거부 정책에서 시작한다. egress를 막으면 DNS 요청도 트래픽이므로 CoreDNS로 가는 UDP·TCP 53 등을 명시적으로 허용해야 서비스 이름을 풀 수 있다.

NetworkPolicy

한쪽 정책만 열었는데 통신이 안 될 때

source Pod의 egress는 허용했지만 destination Pod의 ingress 정책은 source를 허용하지 않는다. 연결 결과는?

  • 양쪽 정책이 모두 허용하지 않아 차단된다
  • source의 egress 허용만으로 연결된다
  • destination 정책은 응답 트래픽에만 적용된다
  • 같은 namespace면 정책과 무관하게 연결된다
  • 사용 중인 CNI가 NetworkPolicy를 구현하는지
  • kubelet의 이미지 가비지 컬렉션 주기
  • StorageClass의 volumeBindingMode
  • Deployment의 revisionHistoryLimit

연결이 허용되려면 source의 egress와 destination의 ingress가 각각 적용되는 정책에서 모두 허용돼야 한다. 응답 트래픽은 허용된 연결의 일부로 처리된다. NetworkPolicy API를 저장하는 것과 실제 데이터 경로에서 집행하는 것은 별개라 CNI 지원이 필요하다.

EndpointSlice

Pod는 Running인데 Service에서 빠질 때

Pod는 Running이지만 readiness probe가 실패한다. 일반 Service의 트래픽은 어떻게 될까?

  • 준비되지 않은 엔드포인트로는 보내지 않는다
  • Running이므로 계속 같은 비율로 보낸다
  • Pod를 즉시 삭제하고 다시 만들지 않는다
  • Service ClusterIP 자체가 삭제된다
  • EndpointSlice
  • ResourceQuota
  • PodDisruptionBudget
  • ClusterRoleBinding

EndpointSlice는 Service의 백엔드 IP·포트와 ready·serving·terminating 상태를 담는다. Pod가 Running이어도 readiness가 실패하면 일반 트래픽 대상에서 빠진다. 그래서 배포 장애에서는 Pod 상태만 보지 않고 EndpointSlice와 readiness 이벤트를 함께 본다.

PART 5

설정 · Secret · 스토리지

설정을 바꿨는데 Pod에 반영되지 않고, PVC가 Pending에 머물며, StatefulSet 교체 뒤 데이터가 엉키는 원인을 다룹니다.

ConfigMap

설정을 바꿨는데 환경 변수가 그대로일 때

ConfigMap 값을 envFrom으로 주입한 뒤 ConfigMap을 수정했다. 실행 중 컨테이너의 환경 변수는?

  • 자동으로 바뀌지 않아 Pod 재시작이 필요하다
  • kubelet 동기화 때 환경 변수도 바로 바뀐다
  • 앱이 다음 요청을 받을 때 자동으로 다시 읽는다
  • Deployment의 replicas가 자동으로 0이 됐다 돌아온다
  • kubelet 동기화 뒤 파일이 갱신될 수 있다
  • 마운트 방식도 반드시 Pod를 다시 만들어야 한다
  • 파일은 즉시 바뀌고 앱 프로세스도 자동 재시작된다
  • ConfigMap 수정 시 볼륨이 영구 삭제된다

환경 변수는 프로세스 시작 때 만들어져 실행 중 자동 변경되지 않는다. ConfigMap 볼륨은 kubelet 동기화와 캐시 지연 뒤 파일이 갱신될 수 있지만 앱이 파일을 다시 읽는지는 별개다. 확실한 배포를 위해 설정 체크섬을 Pod 템플릿에 넣어 롤아웃하는 패턴도 쓴다.

ConfigMap

파일 하나만 마운트하자 갱신이 멈출 때

ConfigMap 키 하나를 subPath로 파일에 마운트했다. ConfigMap을 바꾼 뒤 파일은?

  • 실행 중 Pod에는 자동 갱신되지 않는다
  • 전체 볼륨보다 더 빠르게 갱신된다
  • 키가 바뀔 때마다 컨테이너가 자동 재시작된다
  • subPath를 쓰면 ConfigMap이 Secret으로 변환된다
  • 마운트된 디렉터리가 기존 파일을 가린다
  • 기존 파일과 키가 자동으로 병합된다
  • 이미지 파일이 ConfigMap으로 복사된다
  • 기존 파일이 영구히 이미지에서 삭제된다

ConfigMap·Secret의 subPath 마운트는 자동 갱신을 받지 않는다. 또한 볼륨을 디렉터리에 마운트하면 이미지에 있던 같은 경로의 내용이 가려진다. 기존 설정 파일 일부만 유지해야 하면 마운트 경로와 앱의 설정 포함 방식을 설계해야 한다.

Secret

base64라서 안전하다고 착각할 때

Secret manifest의 data 값이 base64이므로 Git에 커밋해도 안전하다는 판단은?

  • 틀리다. base64는 암호화가 아니라 인코딩이다
  • 맞다. API 서버만 원문으로 복호화할 수 있다
  • 맞다. namespace 밖에서는 디코딩할 수 없다
  • 틀리다. base64는 해시라 원문을 검증만 할 수 있다
  • API 데이터의 저장 시 암호화를 설정한다
  • Secret 이름을 무작위 UUID로 바꾼다
  • 모든 Secret을 ConfigMap으로 변환한다
  • Pod의 imagePullPolicy를 Always로 둔다

base64는 누구나 되돌릴 수 있다. Secret은 권한 분리와 전달 편의를 주지만 기본 etcd 저장이 항상 암호화되는 것은 아니다. 저장 시 암호화, 최소 RBAC, 외부 비밀 관리 연동을 함께 쓰고 manifest 원문을 저장소에 넣지 않는다.

PVC

PVC가 Pending에 머물 때

PVC가 특정 StorageClass와 ReadWriteMany를 요구하지만 이를 만족하는 프로비저너·PV가 없다. 상태는?

  • 조건에 맞는 볼륨이 없어 Pending에 머문다
  • 가장 비슷한 ReadWriteOnce 볼륨에 자동 바인딩된다
  • emptyDir로 자동 대체되어 Pod가 시작된다
  • PVC 용량을 0으로 바꿔 Bound가 된다
  • StorageClass
  • ServiceClass
  • VolumeDeployment
  • NodePort

PVC는 필요한 용량·접근 모드·StorageClass를 요청하고, 조건이 맞는 PV와 바인딩된다. 동적 프로비저너가 없거나 접근 모드를 지원하지 않으면 Pending이다. 이벤트에서 프로비저닝 오류와 토폴로지·용량 조건을 확인한다.

PV 수명

PVC 삭제 뒤 디스크까지 사라질 때

PV reclaimPolicy가 Delete인 동적 볼륨에서 PVC를 삭제하면 일반적으로?

  • PV와 연결된 외부 저장소도 삭제 대상이 된다
  • 데이터가 항상 영구 보존된다
  • PVC만 이름이 바뀌고 PV는 Bound로 남는다
  • StatefulSet이 자동으로 새 PVC를 같은 데이터에 연결한다
  • Retain
  • Restart
  • Recreate
  • RollingUpdate

reclaimPolicy는 claim이 풀린 뒤 PV와 실제 저장소를 어떻게 할지 정한다. Delete는 지원되는 외부 볼륨도 함께 삭제할 수 있고, Retain은 관리자가 데이터를 확인하고 재사용·삭제하도록 남긴다. 중요한 데이터는 정책과 별개로 백업한다.

StatefulSet

복제본마다 저장소와 이름이 필요할 때

DB 복제본마다 안정된 이름과 전용 PVC가 필요하다. 적합한 워크로드는?

  • StatefulSet과 복제본별 PVC
  • Deployment와 하나의 emptyDir
  • DaemonSet과 ConfigMap
  • Job과 hostPort
  • Headless Service
  • ExternalName Service
  • NodePort만 있는 Service
  • PodDisruptionBudget

StatefulSet은 순서가 있는 안정된 Pod 이름을 유지하고 volumeClaimTemplates로 복제본마다 PVC를 만든다. Headless Service는 개별 Pod를 찾을 DNS 레코드를 제공한다. StatefulSet을 지워도 PVC가 자동 삭제되지 않는 구성이 일반적이므로 정리 정책을 확인한다.

임시 볼륨

같은 Pod의 컨테이너끼리 파일을 나눌 때

init container가 만든 파일을 같은 Pod의 app container가 읽게 하되 Pod 삭제 후 보존은 필요 없다. 적합한 볼륨은?

  • emptyDir
  • 각 컨테이너의 독립 쓰기 레이어
  • ClusterRole
  • LoadBalancer Service
  • Pod가 유지되는 동안 남아 있다
  • 컨테이너 재시작마다 반드시 삭제된다
  • 자동으로 PV에 복제된다
  • 노드와 무관하게 영구 보존된다

emptyDir은 Pod가 노드에 배치될 때 만들어져 같은 Pod의 컨테이너들이 공유한다. 컨테이너 재시작에는 남지만 Pod가 노드에서 제거되면 사라진다. 영속 데이터에는 PVC를 쓰고, 메모리 매체를 고르면 노드 메모리 사용량도 고려한다.

운영 · 오토스케일링 · 보안

노드 유지 보수, 자동 확장, RBAC, ServiceAccount와 컨테이너 권한을 실제 운영 경계에 맞춰 설정합니다.

QoS · 퇴거

노드 메모리가 부족할 때 먼저 밀려나는 Pod

CPU·메모리 request와 limit가 전혀 없는 Pod의 QoS 등급은?

  • BestEffort
  • Guaranteed
  • Burstable
  • Critical
  • 모든 컨테이너의 CPU·메모리 request와 limit가 같음
  • limit 없이 request만 가장 크게 설정
  • 모든 컨테이너에 liveness probe만 설정
  • replicas와 maxSurge를 같은 값으로 설정

Kubernetes는 request·limit 구성으로 Guaranteed, Burstable, BestEffort를 정하고 노드 압박 시 퇴거 순서에 활용한다. Guaranteed라도 limit 초과나 더 심한 압박에서 절대 종료되지 않는 것은 아니다. 실제 사용량과 여유를 측정해 값을 잡는다.

HPA

CPU 자동 확장이 계산되지 않을 때

CPU 평균 사용률 기준 HPA인데 Pod에 CPU request가 없다. 왜 확장 계산이 안 될 수 있을까?

  • 사용률의 기준이 되는 CPU request가 없어서
  • CPU limit가 request보다 커야만 HPA가 켜져서
  • HPA는 메모리 지표만 지원해서
  • Deployment는 HPA 대상이 될 수 없어서
  • Metrics Server
  • Ingress Controller
  • CSI 스토리지 드라이버
  • imagePullSecret

CPU Utilization은 현재 사용량을 CPU request로 나눈 값이다. request가 없으면 해당 Pod의 사용률을 정의할 수 없다. 리소스 지표는 보통 Metrics Server가 제공하며, 요청 수·큐 길이 같은 확장은 custom 또는 external metrics API가 필요하다.

가용성

노드 drain이 멈출 때

replicas 3인 앱에 PDB minAvailable 2가 있다. 정상 Pod가 3개라면 동시에 허용되는 자발적 중단 수는?

  • 1개
  • 0개
  • 2개
  • 3개
  • 자발적 퇴거를 제한한다
  • 노드 전원 장애에서도 Pod가 절대 사라지지 않는다
  • 컨테이너 OOM 종료를 막는다
  • readiness 실패를 자동 복구한다

PodDisruptionBudget은 drain·클러스터 오토스케일러 같은 자발적 중단에서 동시에 줄일 수 있는 준비된 Pod 수를 제한한다. 하드웨어 장애 같은 비자발적 중단을 막지는 못한다. 단일 복제본에 maxUnavailable 0을 두면 유지 보수가 막힐 수 있다.

RBAC

한 namespace만 읽게 할 때

개발자에게 dev namespace의 Pod 조회만 허용하려면 가장 좁은 조합은?

  • dev의 Role과 RoleBinding
  • cluster-admin ClusterRoleBinding
  • 모든 namespace의 ClusterRoleBinding
  • Pod마다 별도 Service를 생성
  • dev의 RoleBinding이 그 ClusterRole을 참조한다
  • ClusterRoleBinding으로 dev 이름을 적는다
  • ClusterRole을 dev namespace 안에 생성한다
  • ServiceAccount 없이 ClusterRole만 만든다

RoleBinding은 자신이 있는 namespace 범위에서 Role 또는 ClusterRole의 권한을 주고, ClusterRoleBinding은 클러스터 전체에 권한을 준다. 공통 읽기 규칙은 ClusterRole로 정의해도 namespace별 RoleBinding으로 범위를 좁힐 수 있다.

워크로드 신원

모든 Pod가 같은 권한을 쓸 때

API를 전혀 호출하지 않는 Pod에도 기본 ServiceAccount 토큰이 마운트된다. 노출을 줄이려면?

  • 토큰 자동 마운트를 끈다
  • Service를 ExternalName으로 바꾼다
  • Pod IP를 고정한다
  • 모든 Secret을 환경 변수로 바꾼다
  • 전용 ServiceAccount에 최소 RBAC를 바인딩한다
  • default ServiceAccount에 cluster-admin을 준다
  • 컨테이너 안에 관리자 kubeconfig를 굽는다
  • namespace의 모든 Secret 읽기를 함께 허용한다

ServiceAccount는 워크로드의 Kubernetes API 신원이다. 앱마다 전용 계정을 두고 필요한 동작·리소스·namespace만 허용한다. API를 쓰지 않으면 토큰 자동 마운트를 끄면 탈취 가능한 자격 증명을 줄일 수 있다.

SecurityContext

컨테이너 탈출 피해를 줄이기

일반 웹 앱 컨테이너의 기본 보안 설정으로 가장 적절한 조합은?

  • non-root, 권한 상승 금지, capability 제거
  • privileged, hostPID, root 사용자
  • hostNetwork, SYS_ADMIN 추가, 쓰기 가능한 루트
  • root 사용자, Docker 소켓 마운트, 모든 Secret 주입
  • readOnlyRootFilesystem과 쓰기 가능한 /tmp 볼륨
  • privileged와 hostPath /
  • allowPrivilegeEscalation true
  • 모든 경로를 하나의 PVC에 마운트

runAsNonRoot, allowPrivilegeEscalation: false, capability 전체 제거 후 필요한 것만 추가, readOnlyRootFilesystem은 침해 뒤 할 수 있는 일을 줄인다. 쓰기 경로는 emptyDir나 PVC로 명시한다. privileged와 Docker 소켓은 호스트 장악으로 이어질 수 있다.

이미지 배포

같은 태그를 푸시했는데 배포가 안 바뀔 때

Deployment가 myapp:1.0을 쓰는 상태에서 레지스트리의 같은 태그만 새 이미지로 바꿨다. 기존 Pod는?

  • 템플릿이 안 바뀌어 자동 교체되지 않는다
  • 레지스트리 변경을 감지해 즉시 모두 재시작된다
  • kubelet이 실행 중 파일 시스템을 새 이미지로 덮는다
  • Service가 새 이미지 Pod를 자동 생성한다
  • 불변 버전 태그나 이미지 다이제스트를 사용한다
  • latest 태그만 계속 덮어쓴다
  • Pod 이름에 배포 날짜만 넣는다
  • 실행 중 컨테이너에서 패키지를 직접 수정한다

Deployment는 Pod 템플릿이 바뀔 때 새 ReplicaSet을 만든다. 레지스트리의 같은 태그 내용만 바꿔도 실행 중 Pod는 교체되지 않으며, 새 Pod도 노드 캐시·pull 정책에 따라 다른 이미지를 쓸 위험이 있다. 불변 참조로 배포 이력을 명확히 한다.
